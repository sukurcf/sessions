Module 01

GitHub Copilot Advanced.

GitHub Copilot reads plain Markdown files from your repository. You control its behaviour by adding files, not by changing settings.

II. Copilot Advanced · file layout 04

Where the files live.

your-repo/ ├── AGENTS.md # repo-wide rules ├── .github/ │ ├── copilot-instructions.md # repo-wide rules │ ├── instructions/ │ │ └── python.instructions.md # scoped by glob │ ├── prompts/ │ │ └── new-endpoint.prompt.md # /new-endpoint │ ├── agents/ │ │ └── reviewer.agent.md # custom agent │ ├── skills/ │ │ └── release-notes/ │ │ └── SKILL.md # /release-notes │ └── workflows/ │ └── copilot-setup-steps.yml # cloud agent env └── .vscode/ └── mcp.json # MCP servers

Two scopes

Files under .github/ are shared with the team through Git. The same file types also work per user under ~/.copilot/.

All plain Markdown

Each file is Markdown text. Some types add a small YAML block at the top, called frontmatter.

No build step

Save the file and GitHub Copilot picks it up. Commit it and your team gets it too.

Source: code.visualstudio.com/docs/copilot/customization · August 2026

II. Copilot Advanced · repo instructions 05

Two files for repo rules.

# AGENTS.md — repo root, no frontmatter ## Build and test Run `npm ci` then `npm test`. Do not commit without a passing test run. ## Code style Use named exports. No default exports. Every new endpoint needs an integration test. ## Do not touch `db/migrations/` is generated. Edit the schema file instead and run `npm run migrate:gen`.
FileRead by
AGENTS.mdVS Code, Copilot CLI, cloud agent, and other tools that follow the open AGENTS.md format
.github/
copilot-instructions.md		VS Code, github.com, code review, cloud agent

Which one to write

Write AGENTS.md if more than one tool reads your repository. Write copilot-instructions.md if you only use GitHub Copilot. Both are plain Markdown with no frontmatter.

Nested files

You can put an AGENTS.md in a subfolder. The nearest file in the directory tree wins. This is experimental, behind chat.useNestedAgentsMdFiles.

Source: agents.md · code.visualstudio.com/docs/copilot/customization/custom-instructions · August 2026

II. Copilot Advanced · scoped instructions 06

Rules for some files.

# .github/instructions/python.instructions.md --- description: Python rules for this repo applyTo: "**/*.py" --- Use type hints on every public function. Raise `ValueError` for bad input. Never return None to signal an error. Write tests with pytest. Name them `test_<thing>`.
applyTo valueApplies to
"**/*.py"Every Python file
"**/*.ts,**/*.tsx"Two patterns, comma separated
"src/api/**"One folder and everything under it
"**"Every file in the repository

How it works

When a file you are working on matches the glob, GitHub Copilot adds this file to the request. Files that do not match are not sent, so you keep the request small.

If you leave applyTo out

The file is never added on its own. You must reference it by hand in chat.

Source: code.visualstudio.com/docs/copilot/customization/custom-instructions · August 2026

II. Copilot Advanced · prompt files 07

A task you run again.

# .github/prompts/new-endpoint.prompt.md --- description: Add a REST endpoint with tests agent: agent model: Claude Sonnet 5 tools: ['search', 'edit', 'runCommands'] argument-hint: <resource name> --- Add a REST endpoint for ${input:resource}. 1. Add the route in `src/routes/`. 2. Add a request model with validation. 3. Add an integration test. 4. Run `npm test` and fix what fails.

Run it

Type /new-endpoint in chat. The file name is the command name.

VariableValue
${input:name}Asks the user for a value
${input:name:hint}Same, with placeholder text
${selection}The text selected in the editor

Why a file, not a message

A prompt file is reviewed in a pull request like any other code. When the steps change, you change one file.

Source: code.visualstudio.com/docs/copilot/customization/prompt-files · August 2026

II. Copilot Advanced · skills 08

Package a procedure.

# .github/skills/release-notes/SKILL.md --- name: release-notes description: Write release notes from merged pull requests since the last tag. Use when the user asks to prepare a release. argument-hint: <tag> --- ## Steps 1. Run `git log <last-tag>..HEAD --oneline`. 2. Group commits into Added, Fixed, Changed. 3. Write the file to `CHANGELOG.md`.

The name rule

name must match the parent folder name. Lowercase, no dots, no slashes, no colons, up to 64 characters.

The description does the routing

GitHub Copilot reads only the description until the skill is needed. Say what the skill does and when to use it. Up to 1024 characters.

Two ways to load

Type /release-notes, or let GitHub Copilot match the description to your request and load it on its own.

Source: code.visualstudio.com/docs/copilot/customization/skills · August 2026

Module 02

Agent fundamentals.

An agent is a loop. It reads the task, calls a tool, reads the result, and repeats until the task is done or it needs you.

III. Agent fundamentals · the loop 10

What an agent actually does.

USER "Fix the failing test in cart.py" 1. READ task + instruction files + open file 2. PLAN decide the next single step 3. CALL a tool: read_file("tests/cart.py") 4. OBSERVE the tool result goes back into context 5. REPEAT until done, blocked, or out of budget Tools it calls along the way: search find the failing assert read_file load cart.py edit change the function runCommands run pytest ← asks you first runCommands pytest passes ← loop ends

Context is the input

Everything the agent knows comes from the request: your message, the instruction files that match, and the results of tools it already called.

Tools are the output

The model cannot touch your disk. It can only ask to run a tool. The editor runs it and hands back text.

You approve the risky ones

Reading a file is automatic. Running a terminal command asks for confirmation the first time.

III. Agent fundamentals · custom agents 11

Define your own agent.

# .github/agents/reviewer.agent.md --- name: reviewer description: Reviews a diff for security bugs. argument-hint: <pull request number> model: Claude Opus 5 tools: ['search', 'githubRepo', 'runCommands'] agents: ['Explore'] user-invocable: true disable-model-invocation: false --- You review code for security problems only. Read the diff. For each change, check input validation, authentication, and secrets in code. Report file and line. Do not edit any file.
FieldMeaning
nameHow you select it in chat
descriptionWhen it should be picked
toolsThe only tools it may call
agentsAgents it may hand work to
modelWhich model runs it
user-invocableShows in the picker
targetvscode or github-copilot

Folder

.github/agents/ for the team. ~/.copilot/agents/ for you only. Chat mode files (.chatmode.md) are replaced by this format.

Source: code.visualstudio.com/docs/copilot/customization/custom-agents · August 2026

III. Agent fundamentals · tool lists 12

Naming a tool.

# Every tool from one MCP server tools: ['bookshop/*'] # One named tool from that server tools: ['bookshop/find_book'] # Built-in tools and MCP tools together tools: ['search', 'edit', 'bookshop/find_book'] # In the body text, point at one tool Use #tool:bookshop/find_book before you answer.

The format is server slash tool

The part before the slash is the server name from your MCP config file. The part after is the function name in your server.

There is a limit

VS Code sends up to 128 tools in one request. Past that, tools are grouped. The setting is github.copilot.chat.virtualTools.threshold.

Fewer tools work better

A short list makes the choice easy for the model. Use the Configure Tools button in the chat box to turn tools off for a session.

Source: code.visualstudio.com/docs/agents/run/tools · code.visualstudio.com/docs/agents/reference/ai-settings · August 2026

III. Agent fundamentals · delegation 13

One agent calls another.

# .github/agents/release.agent.md --- name: release description: Prepare a release branch. tools: ['search', 'edit', 'runCommands'] agents: ['reviewer', 'Explore'] handoffs: - label: Security review agent: reviewer prompt: Review the release diff. send: true --- Cut the release, then hand the diff to reviewer.

Why split the work

Each agent gets its own context window. A search that reads 40 files does not fill up the main conversation.

agents: accepts three shapes

A list of names, * for every agent, or [] for none. Use [] when an agent must stay in one place.

handoffs are one-way

A subagent runs, returns one message, and stops. It cannot ask the parent a question halfway through. Write the full task in the prompt.

Source: code.visualstudio.com/docs/copilot/customization/custom-agents · August 2026

III. Agent fundamentals · cloud agent 14

Give the cloud agent a machine.

# .github/workflows/copilot-setup-steps.yml name: Copilot setup steps on: [workflow_dispatch] jobs: copilot-setup-steps: # exact name runs-on: ubuntu-latest steps: - uses: actions/checkout@v5 - uses: actions/setup-python@v5 with: python-version: '3.12' - run: pip install -r requirements.txt

The job name is fixed

The job must be called copilot-setup-steps. Any other name is ignored and the agent starts on a bare machine.

What it is for

The cloud agent runs on GitHub, not on your laptop. Without this file it has no dependencies installed, so it cannot run your tests.

Test it like a workflow

It is a normal GitHub Actions file. Trigger it by hand to check that the steps pass before the agent needs them.

Source: docs.github.com/en/copilot · customize the agent environment · August 2026

Module 03

Agentic framework envisioning.

Before you write an agent, decide three things: what it knows, what it can do, and what it is allowed to do without asking.

IV. Envisioning · the three parts 16

Context, tools, policy.

Context — what it knows

Facts the agent cannot guess: your build command, your folder layout, your naming rules.

Ask: what does a new developer need on day one? Write that down.

AGENTS.md · .instructions.md

Tools — what it can do

Actions in your systems: query a database, read a ticket, call an internal API.

Ask: what do you open a second window for? That is a tool.

MCP server · built-in tools

Policy — what needs approval

The line between an action the agent takes alone and one you confirm first.

Ask: which action cannot be undone with git checkout?

tools: list · tool approvals

Most failing agent projects skip the third one. They give an agent every tool, then turn it off after the first bad write.

IV. Envisioning · which file for which job 17

Pick the right layer.

You want to… Use Loaded when
State a rule for the whole repository AGENTS.md Every request
State a rule for one language or folder *.instructions.md with applyTo When a file matches the glob
Repeat a task you do often *.prompt.md You type /name
Teach a multi-step procedure SKILL.md You type /name, or the description matches
Change behaviour, model, and tool access *.agent.md You select the agent, or a parent hands off
Reach a system outside the editor MCP server in mcp.json The agent calls one of its tools

Rule of thumb: start at the top. Move down a row only when the layer above cannot do the job. Every layer you add costs tokens on every request.

IV. Envisioning · where the agent runs 18

Three places to run it.

Agent mode in VS Code

Runs on your machine, in your workspace, with your files open. You watch each step and approve commands.

Use for: work where you want to read the diff as it appears.

Copilot cloud agent

Runs on GitHub. You give it an issue, it works on a branch and opens a pull request.

Use for: small, well-described tasks you do not want to sit through.

GitHub Copilot CLI

Runs in your terminal. Same agent loop, no editor.

npm install -g @github/copilot copilot

Needs Node.js 22 or later.

All three read the same AGENTS.md, the same instruction files, and the same MCP servers. Write the customization once and it follows the work.

Source: docs.github.com/en/copilot · install Copilot CLI · August 2026

Module 04

Agents and MCP.

The Model Context Protocol is one standard way for an agent to call a tool you wrote. Write the server once, use it in every client.

V. MCP · architecture 20

Host, client, server.

Host

VS Code · GitHub Copilot CLI · cloud agent. Runs the model, keeps the conversation, asks you to approve actions.

Client

One connection per server. Created by the host. You do not write this part.

↓  JSON-RPC 2.0  ↓

Server · stdio

A local process the host starts. Messages travel over standard input and output.

Server · Streamable HTTP

A server behind a URL. One deployment serves many developers.

You build one box

Of the four boxes on the left, only the server is yours. The host and the client already exist.

Write once, use everywhere

The same server works in VS Code, in the CLI, and in the cloud agent. The protocol is the same in all three.

Pick stdio to start

A stdio server needs no port, no deployment, and no authentication. Move to HTTP when other people need the same server.

Source: modelcontextprotocol.io/docs/learn/architecture · August 2026

V. MCP · what a server exposes 21

Three things a server offers.

Tools

Functions the model can call. This is the one you will use most.

@mcp.tool() def find_book(q: str) -> str: ...

Chosen by: the model, during the loop.

Resources

Read-only data at a URI. Like a GET request with no side effects.

@mcp.resource("catalog://{isbn}") def book(isbn: str) -> str: ...

Chosen by: the host application.

Prompts

Message templates your server ships, so users do not retype them.

@mcp.prompt() def review(title: str) -> str: ...

Chosen by: the user, from a menu.

If you are not sure which one to write, write a tool. Resources and prompts are optional; almost every real server is a set of tools.

V. MCP · on the wire 22

What travels on the wire.

// request { "jsonrpc": "2.0", "id": 3, "method": "tools/call", "params": { "name": "find_book", "arguments": { "query": "Dune" } } } // result { "jsonrpc": "2.0", "id": 3, "result": { "content": [{ "type": "text", "text": "Found 3 books." }] } }
MethodDoes
server/discoverAsk what the server offers
tools/listList tools
tools/callRun one tool
resources/listList resources
resources/readRead one resource
prompts/listList prompts
prompts/getGet one prompt
subscriptions/listenWatch for changes

The SDK writes all of this

You never build these messages by hand. You write a Python function; the SDK produces the schema, parses the call, and formats the result.

V. MCP · VS Code configuration 23

The config file.

// .vscode/mcp.json { "inputs": [ { "id": "api-key", "type": "promptString", "description": "Catalog API key", "password": true } ], "servers": { "bookshop": { "type": "stdio", "command": "uv", "args": ["run", "server.py"], "cwd": "${workspaceFolder}/bookshop", "env": { "API_KEY": "${input:api-key}" } }, "catalog": { "type": "http", "url": "https://api.example.com/mcp", "headers": { "Authorization": "Bearer ${input:api-key}" } } } }
KeyMeaning
serversName to configuration
inputsValues to ask the user for
sandboxFile and network limits
typestdio, http, or sse
dev.watchRestart on file change

Never put a secret in this file

Declare an input with "password": true and reference it as ${input:api-key}. VS Code asks once and stores the value securely. The file stays safe to commit.

Two locations

.vscode/mcp.json for this workspace. Your user profile for every workspace: run MCP: Open User Configuration.

V. MCP · CLI and cloud agent 24

The same server, elsewhere.

# GitHub Copilot CLI — add a local server copilot mcp add bookshop -- uv run server.py # Add a remote server copilot mcp add --transport http catalog \ https://api.example.com/mcp # Manage them from inside a session /mcp list /mcp show bookshop /mcp edit bookshop /mcp delete bookshop # Config file the CLI writes ~/.copilot/mcp-config.json

Cloud agent

Configure servers in the repository: Settings → Copilot → MCP servers. The JSON uses an mcpServers key.

Cloud agent limits

List the tools you allow in a tools array. Store secrets as repository secrets whose names start with COPILOT_MCP_.

Portable config

A workspace .mcp.json or a user ~/.copilot/mcp-config.json is read directly by the agent host, so the same file serves more than one tool.

Module 05

Custom MCP workshop.

Seven labs. Build a server in Python, run it, test it, and connect it to GitHub Copilot in VS Code.

Python SDK v2.0.0 · Python 3.10 or higher

VI. Workshop · lab 0 26

Set up the project.

# macOS and Linux uv init bookshop cd bookshop uv venv source .venv/bin/activate uv add "mcp[cli]" touch server.py # Windows # .venv\Scripts\activate # new-item server.py
bookshop/ ├── pyproject.toml # uv wrote this ├── server.py # your server ├── test_server.py # lab 5 └── .venv/

Why the [cli] extra

It adds the mcp command: mcp dev, mcp run, and mcp install. Plain mcp gives you the library only.

Pin the major version

pip install mcp now installs 2.x. If a library of yours still needs the old API, keep an upper bound such as mcp>=1.28,<2.

Source: modelcontextprotocol.io/docs/develop/build-server · github.com/modelcontextprotocol/python-sdk · August 2026

VI. Workshop · lab 1 27

A server in fifteen lines.

# server.py from mcp.server import MCPServer mcp = MCPServer("Bookshop") @mcp.tool() def add(a: int, b: int) -> int: """Add two numbers.""" return a + b @mcp.resource("greeting://{name}") def greeting(name: str) -> str: """Greet someone by name.""" return f"Hello, {name}!"

Open it in the Inspector

uv run mcp dev server.py

Call add with a=1, b=2 and you get 3 back.

What you did not write

No JSON Schema. No request parsing. No validation code. No protocol handling. a: int, b: int is the schema.

Renamed in v2

The class used to be FastMCP from mcp.server.fastmcp. In v2 it is MCPServer from mcp.server. The old import path was removed, not deprecated.

Source: github.com/modelcontextprotocol/python-sdk · py.sdk.modelcontextprotocol.io/whats-new · August 2026

VI. Workshop · lab 2 28

Typed inputs and errors.

from pydantic import BaseModel from mcp import MCPError from mcp.server import MCPServer from mcp.types import INVALID_PARAMS mcp = MCPServer("Bookshop") class Book(BaseModel): title: str author: str @mcp.tool() def find_book(query: str, limit: int = 5) -> list[Book]: """Search the catalog by title or author. Args: query: Words to match in a title or an author name. limit: How many books to return. Must be 1 or more. """ if limit < 1: raise MCPError(INVALID_PARAMS, "limit must be 1 or more") return [Book(title="Dune", author="Herbert")]

The schema comes from the hints

Type hints become the input schema. A Pydantic model as the return type becomes the structured output schema.

Two kinds of failure

MCPError is a protocol error. The model never sees it. Every other exception becomes a result marked as an error, which the model reads and can act on.

Choose on purpose

Raise MCPError for a broken call the model cannot fix. Raise a normal ValueError when you want the model to read the message and try again.

Source: py.sdk.modelcontextprotocol.io/servers/handling-errors · August 2026

VI. Workshop · lab 3 29

Resources and prompts.

# A fixed resource: one URI, no parameters @mcp.resource("catalog://recent") def recent() -> str: """The ten newest titles.""" return "Dune\nNeuromancer\nSolaris" # A templated resource: {isbn} is a parameter @mcp.resource("catalog://book/{isbn}") def record(isbn: str) -> str: """Return one catalog record.""" return f"ISBN {isbn}: Dune, Herbert, 1965" # A prompt: a message the user can pick @mcp.prompt() def review_request(title: str) -> str: """Ask for a short review of one book.""" return f"Write three sentences about {title}."

Resource or tool?

A resource reads data and changes nothing. A tool may change something. If in doubt, and the model should decide when to call it, make it a tool.

URI templates are RFC 6570

In v2 the templates follow the standard, so {+path} and {?query} work. Matching is exact, and path traversal in extracted values is rejected by default.

Errors are caught early

A template that is not valid fails when the decorator runs, at import time. You do not wait for the first request to find out.

Source: py.sdk.modelcontextprotocol.io/servers/uri-templates · August 2026

VI. Workshop · lab 4 30

Run it, two ways.

# server.py — bottom of the file if __name__ == "__main__": mcp.run(transport="stdio") # Open in the MCP Inspector uv run mcp dev server.py # Run over stdio, the local default uv run mcp run server.py # Run over HTTP for a deployed server uv run mcp run server.py \ --transport streamable-http
TransportUse it for
"stdio"A local process the editor starts
"streamable-http"A server you deploy behind a URL
"sse"Older clients only

Transport options live on run()

MCPServer(...) describes what your server is. run() decides how it is served. MCPServer("x", port=9000) raises a TypeError in v2.

Never print on stdio

print() writes to stdout, which is the message channel. One print corrupts the JSON and breaks the server. Use the logging module, which writes to stderr.

Source: py.sdk.modelcontextprotocol.io/run · modelcontextprotocol.io/docs/develop/build-server · August 2026

VI. Workshop · lab 6 31
