1 What Are ADO Area Paths?

Area Paths in Azure DevOps organize work items into a hierarchical tree structure

📁 Project (Root)
MyProject
🖥️ Frontend
React · Angular · Mobile
⚙️ Backend
API · Services · DB
🔧 DevOps
CI/CD · Infra · Monitoring

🎯 Team Routing

Assign work items to teams via area paths automatically

🔍 Filtered Views

Boards and queries scoped to specific areas

🔐 Access Control

Restrict who can view/edit items per area path

ADO Area Paths → GitHub Equivalents

GitHub doesn't have "Area Paths" — use these 4 strategies together

ADO Concept GitHub Equivalent How It Works
Area Path hierarchyLabels (area/*)Prefix-based labels: area/frontend, area/backend, area/api
Area Path on boardsCustom Field (Single-select)Project field "Area" with dropdown options, filterable in board/table views
Area → Team routingGitHub TeamsCreate teams per area, assign repos, use @team mentions
Area-based reviewsCODEOWNERSAuto-assign reviewers based on file paths in the repo
Filtered board viewsProject Saved ViewsCreate saved views filtered by label or custom field per area
Hierarchical nestingNested Teams + Sub-issuesTeams with sub-teams, issues with up to 8 levels of sub-issues
💡 Recommendation: Use Labels for cross-repo categorization + Custom Fields for project-level tracking + Teams for access control + CODEOWNERS for code review routing.

Tutorial: Create Teams in GitHub (UI)

Step-by-step walkthrough in the GitHub web interface

1
Navigate to Teams
Go to github.com/orgs/YOUR_ORG → click Teams tab in the top navigation bar
2
Create New Team
Click the green "New team" button on the right side
3
Configure Team Details
Team name: e.g., frontend-devs · Description: "Frontend engineering team" · Visibility: Visible (recommended) or Secret · Parent team: Select a parent for nesting (optional)
4
Add Members
On the team page → Members tab → "Add a member" → search by username → set role: Member or Maintainer
5
Assign Repositories
Team page → Repositories tab → "Add repository" → search repo → set permission: Read, Write, or Admin

👁️ Visible Teams

All org members can see and @mention the team. Can be nested.

🔒 Secret Teams

Only team members and org owners can see it. Cannot be nested.

🏗️ Nested Teams

Child teams inherit parent repo permissions. Great for area hierarchies.

Tutorial: Create Area Labels

Create area/* prefixed labels to replicate ADO area path categorization

🖥️ Via GitHub UI

1
Open Labels page
Go to Repo → Issues tab → click "Labels" button (next to Milestones)
2
Create New Label
Click "New label" → Name: area/frontend → Description: "Frontend UI components" → Pick a color (e.g., blue)
3
Repeat for each area
Create: area/backend (green), area/api (purple), area/devops (orange), area/docs (cyan)
4
Set Org Defaults
Org Settings → Repository defaults → Labels → add your area labels so every new repo inherits them

⌨️ Via gh CLI

🏷️ Create Labels

gh label create "area/frontend" \
  --color "1D76DB" \
  --description "Frontend UI" \
  -R ORG/REPO

gh label create "area/backend" \
  --color "0E8A16" \
  --description "Backend services" \
  -R ORG/REPO

🔁 Bulk Create Across Repos

REPOS=("org/repo1" "org/repo2")
LABELS=(
  "area/frontend:1D76DB:Frontend"
  "area/backend:0E8A16:Backend"
)
for repo in "${REPOS[@]}"; do
  for info in "${LABELS[@]}"; do
    IFS=':' read -r n c d <<< "$info"
    gh label create "$n" --color "$c" \
      --description "$d" --force \
      -R "$repo"
  done
done

Tutorial: Create "Area" Custom Field

Add a Single-select "Area" field to your GitHub Project for board filtering

🖥️ Via GitHub UI

1
Open your Project
Go to Org → Projects tab → click your project → switch to Table view
2
Add a new field
Click the + column header (rightmost) → select "New field"
3
Configure the field
Name: Area → Field type: Single select → Add options: Frontend, Backend, API, Infrastructure, DevOps
4
Set option colors
Project Settings (⚙️ gear icon) → click "Area" field → click each option → assign a distinct color
5
Create filtered views
Click "New view" → name it "Frontend Board" → add filter: Area:Frontend → Save

⌨️ Via gh CLI

# Create "Area" single-select field on project #1
gh project field-create 1 --owner "ORG" --name "Area" \
  --data-type "SINGLE_SELECT" \
  --single-select-options "Frontend,Backend,API,Infra,DevOps"

# Create other useful fields
gh project field-create 1 --owner "ORG" --name "Story Points" --data-type "NUMBER"
gh project field-create 1 --owner "ORG" --name "Component" --data-type "TEXT"
💡 Pro Tip: Group the Board view by "Area" to see columns per area (like ADO area-scoped boards). Up to 50 options per single-select field. Filter with Area:Frontend,Backend for multi-select views.

CODEOWNERS — Area-Based Code Review Routing

Automatically assign reviewers based on file paths — replicates ADO area-based assignment

📄 .github/CODEOWNERS File

# .github/CODEOWNERS

# Frontend team owns all UI code
/src/frontend/     @myorg/frontend-devs
/src/components/   @myorg/frontend-devs
*.tsx              @myorg/frontend-devs

# Backend team owns server code
/src/backend/      @myorg/backend-devs
/src/api/          @myorg/api-team

# DevOps team owns infra
/.github/          @myorg/devops-team
/terraform/        @myorg/devops-team
Dockerfile         @myorg/devops-team

# Docs team
/docs/             @myorg/docs-team

# Security team reviews all deps
package-lock.json  @myorg/security-team

⚡ How It Works

  • PR modifies /src/frontend/ → frontend-devs auto-requested
  • PR modifies Dockerfile → devops-team auto-requested
  • Last matching pattern wins (order matters)
  • Enable branch protection → require CODEOWNERS review
📌 Setup: Place the file in .github/CODEOWNERS, docs/CODEOWNERS, or repo root. Enable "Require review from Code Owners" in branch protection rules.

2 Tutorial: Provide User Access to Areas

🖥️ Repository Access (UI)

1
Open Repo Settings
Go to Repo → Settings tab → "Collaborators and teams" in the left sidebar (under Access)
2
Add a Team
Click "Add teams" → search for your team (e.g., frontend-devs) → select it
3
Set Role
Choose: Read (view only) · Triage (manage issues) · Write (push code) · Maintain (manage repo) · Admin (full control)

🖥️ Project Access (UI)

1
Open Project Settings
Open your Project → click ⚙️ (Settings) → "Manage access" in the sidebar
2
Invite Team
Click "Invite collaborators" → search team name → set role: Read, Write, or Admin

⌨️ Via CLI

# Grant team Write access to a repo (push = Write)
gh api orgs/ORG/teams/frontend-devs/repos/ORG/my-app -X PUT -f permission="push"

# Grant team Read access (pull = Read)
gh api orgs/ORG/teams/readonly-team/repos/ORG/my-app -X PUT -f permission="pull"

# Set org base permission to "none" (most restrictive)
gh api orgs/ORG -X PATCH -f default_repository_permission="none"
⚠️ Key Difference from ADO: ADO restricts access per area path. GitHub restricts access per repository via teams. To isolate areas, use separate repos per area or CODEOWNERS for review gates.
⚖️

Access Model Comparison — ADO vs GitHub

🔶 Azure DevOps

  • Area Path security per node
  • Users see only their area's work items
  • Inherited permissions down the tree
  • Security set at project + area level
  • Fine-grained per work item type

🟣 GitHub

  • Team-based access at repo level
  • Users see all issues in repos they access
  • Nested teams inherit parent permissions
  • CODEOWNERS for review routing
  • Project views filter what users focus on

🛡️ Strategy 1: Multi-Repo

Split code by area into separate repos. Each team gets access only to their repos. Strongest isolation.

👥 Strategy 2: Mono-Repo + Teams

Single repo with CODEOWNERS. Everyone reads code, but only area owners can approve PRs.

📊 Strategy 3: Project Views

Create per-team saved views filtered by Area field or labels. Focused view without restricting access.

3 Tutorial: Create Iterations (UI)

Iterations are project-scoped sprint fields — currently UI-only (no CLI/API to create them)

1
Open Project in Table view
Go to Org → Projects → open your project → switch to Table view (top tabs)
2
Add Iteration field
Click the + column header → "New field" → Name: Sprint → Type: Iteration
3
Set start date and duration
Pick a start date → set duration (e.g., 2 weeks). GitHub auto-creates 3 iterations initially.
4
Add more iterations
Go to Project Settings ⚙️ → click "Sprint" field → "Add iteration" button → set dates for each sprint
5
Add breaks (optional)
In Settings → Sprint field → click "Insert break" between iterations for holidays or code freezes
6
Create filtered views
Click "New view" → name it "Current Sprint" → add filter: Sprint:@current → save. Also try @next, @previous

📅 @current

Filter for the active sprint based on today's date

⏭️ @next

Filter for the upcoming sprint for backlog grooming

⏮️ @previous

Filter for the last sprint for retrospective reviews

📌 No CLI for creation: Iteration fields can only be created via UI. However, you can assign items to iterations via GraphQL: updateProjectV2ItemFieldValue mutation with the iteration option ID.

4 Tutorial: Create Work Items (UI)

In GitHub, Issues are the equivalent of ADO Work Items

🖥️ Create an Issue via GitHub UI

1
Open Issues

2
Choose template (if configured)
Select a template (Bug Report, Feature Request) or click "Open a blank issue"
3
Fill in details
Title: descriptive name · Body: description in Markdown · Issue type: select Bug/Task/Feature from the type dropdown
4
Set metadata (right sidebar)

🖥️ Add Sub-Issues & Link PRs

🔗 Add Sub-Issues (UI)

  • Open a parent issue (e.g., an Epic)
  • Click "Add sub-issue" button
  • Create a new sub-issue or link existing
  • Up to 100 sub-issues per parent
  • Up to 8 levels of nesting
  • Parent shows a progress bar

⌨️ Create Issue via CLI

# Create an issue
gh issue create \
  --title "Fix login timeout" \
  --body "Steps to reproduce..." \
  --label "bug,area/frontend,P1" \
  --assignee "@me" \
  -R ORG/REPO

# Add to project
gh project item-add 1 \
  --owner ORG \
  --url "ISSUE_URL"

# Close an issue
gh issue close 42 -R ORG/REPO

Tutorial: Configure Issue Types (UI)

Issue types are configured at the organization level — up to 25 custom types

1
Navigate to Org Settings
Go to github.com/organizations/YOUR_ORG/settings → scroll to "Planning" section → click "Issue types"
2
View default types
GitHub provides 3 defaults: Bug Feature Task
3
Create custom types
Click "Create type" → Name: Epic → pick an icon and color → Save. Repeat for: Spike, Research, Debt, etc.
4
Enable on repos
Issue types apply to all repos in the org. When creating an issue, the type dropdown appears automatically.

🎯 Epic

Large initiative. Create as parent issue with sub-issues for Features/Stories.

✨ Feature

New capability. Sub-issue of Epic, parent of Tasks.

✅ Task

Individual work item. Leaf-level, assigned to one person.

💡 Filter by type in Projects: Use type:Bug or type:Epic in project view filters. Group your board by issue type to see columns per type.

Issue Templates & Forms

Standardize work item creation with YAML-based issue forms

📝 Issue Form (YAML)

# .github/ISSUE_TEMPLATE/bug-report.yml
name: Bug Report
description: Report a bug
labels: ["bug", "triage"]
body:
  - type: input
    id: title
    attributes:
      label: Bug Summary
    validations:
      required: true
  - type: dropdown
    id: area
    attributes:
      label: Area
      options:
        - Frontend
        - Backend
        - API
        - Infrastructure
  - type: textarea
    id: steps
    attributes:
      label: Steps to Reproduce
  - type: dropdown
    id: priority
    attributes:
      label: Priority
      options:
        - P0 - Critical
        - P1 - High
        - P2 - Medium
        - P3 - Low

📂 Template Config

# .github/ISSUE_TEMPLATE/config.yml
blank_issues_enabled: false
contact_links:
  - name: Feature Request
    url: "https://github.com/ORG/REPO/discussions/new?category=ideas"
    about: Suggest a feature
  • Place templates in .github/ISSUE_TEMPLATE/
  • Issue Forms (YAML) render as structured forms
  • Issue Templates (Markdown) provide pre-filled text
  • Disable blank issues to enforce templates
  • Add contact links for external resources
💡 Tip: Add an "Area" dropdown in your issue form to replicate ADO's area path picker on the work item form.

Work Item Migration Using Josh Johanning's Script

⬇️ Practical flow from ado_workitems_to_github_issues: prerequisites → run script → verify output

✅ Script Migrates

  • Title and description
  • Bug repro steps and system info (for Bug type)
  • Acceptance criteria in issue body
  • Closed states mapped to closed GitHub issues
  • Original ADO URL + details table + raw JSON in comments
  • Optional ADO comments section
  • Optional assignee mapping from ADO email to GitHub username

⚠️ Known Limits / Notes

  • Created/updated timestamps are not preserved
  • Create lower-case labels per work item type first
  • Scope migration with an Area Path (WIQL uses UNDER)
  • -ado_production_run updates ADO items with copied-to-github tag
  • -gh_update_assigned_to may trigger assignment emails
⚠️ Repository approach: Run ado_workitems_to_github_issues.ps1 with PATs for ADO + GitHub, scoped to an area path, and optionally mark source items with copied-to-github to avoid duplicates.

Run Locally (PowerShell)

📤 Script Invocation Pattern

./ado_workitems_to_github_issues.ps1 `
  -ado_pat "abc" `
  -ado_org "my-ado-org" `
  -ado_project "PartsUnlimited" `
  -ado_area_path "PartsUnlimited\migrate" `
  -ado_migrate_closed_workitems `
  -ado_production_run `
  -gh_pat "ghp_xxx" `
  -gh_org "my-github-org" `
  -gh_repo "migrate-ado-workitems" `
  -gh_update_assigned_to `
  -gh_assigned_to_user_suffix "" `
  -gh_add_ado_comments

Phase 4 — Validate & Verify

✅ Validation Checklist

  • Review migrated issue body includes ADO source URL
  • Confirm closed ADO states closed matching GitHub issues
  • Verify assignee mapping and labels per work item type
  • Check ADO item has copied-to-github tag (production mode)
  • Re-run safely using tag-based duplicate protection

📊 Post-Migration Steps

  • Use PATs/secrets rotation before and after migration runs
  • Run smaller area-path batches to reduce retry complexity
  • Communicate assignee-email notifications before running with assignment mapping
  • Keep script config and run logs for audit evidence
  • Do a dry run before enabling -ado_production_run

Key Takeaways

🗂️ Area Paths & Teams

ADO area paths → GitHub Labels (area/*) + Custom Fields + Teams + CODEOWNERS. Use all 4 together for full coverage.

🔄 Iterations

Create iteration fields in GitHub Projects. Export ADO iterations via API and recreate manually. Use @current/@next filters.

🔐 Access Control

GitHub uses repo-level + team-based access (not area-level). Use multi-repo strategy or CODEOWNERS for area isolation.

📝 Work Items

Issues = work items. Use issue types, sub-issues (8 levels), and issue forms. GEI doesn't migrate work items — use custom scripts.
