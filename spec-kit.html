PART I

Why spec-driven development.

The problem Spec Kit was built to solve, and the process it puts in its place.

II. Why · The problem 05

One long prompt is not a design.

Asking an agent to "build the thing" in a single prompt hides every decision inside a chat transcript. Spec Kit pulls those decisions out into files you can read, review, and version.

AspectOne-shot promptingSpec-driven development
Source of truthThe chat history, lost when the session endsFiles in the repo: spec, plan, tasks
AmbiguityThe model guesses, and you find out at review timeSurfaced and resolved before any code is written
Review pointA large diff, after all the work is doneFour small checkpoints, each cheap to change
ReworkRe-prompt and hope the next attempt is closerFix the artifact that owns the problem, re-run
Team scaleOnly the prompter knows what was intendedIntent is written down and shared in the PR
Agent contextRebuilt from scratch every conversationRead back from the artifacts on every command

Idea · Specifications become executable — they generate the implementation instead of just describing it

III. Why · Core philosophy 06

Spec-Driven Development.

A structured process where you write down the intent first and let the agent handle the implementation detail. Four ideas hold it together.

Intent before implementation

The specification defines the what and why. The tech stack, architecture, and libraries are a separate, later decision.

Guardrails, not vibes

A project constitution states the principles every later phase is checked against — testing standards, security rules, architecture limits.

Multi-step refinement

Not one giant generation. Each step produces an artifact you can correct before the next step consumes it.

Works greenfield and brownfield

Start a new project from requirements, explore parallel implementations, or add features to and modernize an existing codebase.

Read · github.github.io/spec-kit/concepts/sdd.html  ·  spec-driven.md in the repo

IV. Why · Two halves 07

Two halves, one toolkit.

Spec Kit is a command line tool and a set of prompts. Keeping them apart makes everything else easier to follow.

Half one · You run this

The specify CLI

A Python CLI installed once on your machine. It scaffolds a project, writes the command files your agent understands, and manages integrations, extensions, presets, and bundles. It never writes your application code.

specify init specify check specify integration specify extension

Half two · Your agent runs this

The /speckit.* commands

Prompt files installed into your coding agent by init. Each one is a scripted process — read the current artifacts, apply a template, write the next artifact. This is where the actual work happens.

/speckit.specify /speckit.plan /speckit.tasks /speckit.implement

Note · Spec Kit does not replace your agent. It supplies the process; the agent supplies the intelligence

What lands in your repo.

.specify/ · the toolkit

Templates, helper scripts, and state. constitution.md holds your project principles; feature.json records which feature is active — Spec Kit resolves the feature from that file, not from the checked-out Git branch.

Agent directory · the commands

Written by init for the integration you chose. Copilot gets .github/agents/ and .github/prompts/; Claude Code gets .claude/skills/; Gemini gets .gemini/commands/.

specs/ · the feature work

One numbered directory per feature, holding spec.md, plan.md, tasks.md and any supporting design artifacts. These are the files you review in the pull request.

Scripts

Installed as .specify/scripts/bash/, powershell/, or python/ depending on --script.

PART II

Installing the Specify CLI.

Prerequisites, the install routes, initializing a project, and confirming it worked.

VI. Install · Prerequisites 10

Before you start.

Spec Kit ships as a Python package. Four things need to be in place.

Python 3.11 or newer

The Specify CLI is a Python application. Linux, macOS, and Windows are all supported — PowerShell scripts work without WSL.

uv (recommended) or pipx

uv is the recommended package manager for a persistent install. pipx and plain pip also work.

A supported AI coding agent

GitHub Copilot, Claude Code, Gemini CLI, Codex CLI, Cursor and 30+ others. CLI agents must be installed; IDE agents work through the IDE.

Git — optional

Git is only required once you enable the git extension. Repository init and feature branching are no longer part of the default setup.

Docs · github.github.io/spec-kit/installation.html  ·  Latest release: 0.14.x

VII. Install · Specify CLI 11

Install the Specify CLI.

# From PyPI — simplest uv tool install specify-cli # Pin an exact version uv tool install specify-cli==0.12.11 # From source, pinned to a release tag uv tool install specify-cli --from \ git+https://github.com/github/spec-kit.git@vX.Y.Z # Alternatives pipx install specify-cli pip install specify-cli # Confirm it works specify version specify check
Two official channels

The specify-cli package on PyPI, and the github/spec-kit repository for source installs. Both are maintained by the Spec Kit team; either route is supported.

Pinning

When installing from source, keep the leading v on the tag — v0.12.11, not 0.12.11.

One-time run

uvx runs the CLI without installing it. Useful for trying it out, but it does not update the persistent specify on your PATH.

Staying current

specify self check reports whether a newer release exists and changes nothing. specify self upgrade performs the upgrade; add --dry-run to preview it or --tag vX.Y.Z to pin.

Air-gapped

Locally built wheels are supported — see the air-gapped installation guide.

VIII. Install · Initialize 12

Initialize a project.

# New directory, GitHub Copilot specify init my-project --integration copilot # Current directory instead specify init --here --integration claude # Merge into a non-empty directory specify init --here --force # PowerShell scripts, plus a preset specify init my-project --script ps \ --integration copilot --preset compliance # Copilot as agent skills, not prompt files specify init my-project --integration copilot \ --integration-options="--skills"
FlagWhat it does
--integration <key>Which coding agent to scaffold for
--integration-optionsAgent-specific options, e.g. --skills
--script sh|ps|pyBash, PowerShell, or Python helpers
--hereUse the current directory
--forceMerge into an existing directory
--ignore-agent-toolsSkip the agent CLI presence check
--preset <id>Install a preset during init

Omit --integration and an interactive terminal prompts you to choose. Non-interactive runs, such as CI, default to GitHub Copilot.

XII. Commands · Quality gates 17

Optional quality gates.

None of these write application code. They are there to catch a problem while it is still a paragraph, not a pull request.

CommandRun itWhat it does
/speckit.clarifyBefore /speckit.planAsks up to five targeted questions about underspecified areas and writes your answers back into spec.md. Run it repeatedly, one area at a time
/speckit.checklistAny time after the specGenerates a quality checklist — unit tests for your requirements. Checks the spec for completeness, clarity, and consistency rather than testing code
/speckit.analyzeAfter /speckit.tasks, before implementingRead-only consistency analysis across spec.md, plan.md, and tasks.md. Reports conflicts, gaps, and ambiguities. Never edits files

When a gate flags something, fix it at the source and re-run: requirement problems go back to /speckit.clarify or /speckit.specify, design problems to /speckit.plan, then regenerate with /speckit.tasks.

XIII. Commands · Choosing a path 18

How much process?

Two paths are common. Match the ceremony to the risk — a throwaway script does not need three quality gates, and a payments flow does.

Shorter path

Small, low-risk features

  • /speckit.specify
  • /speckit.plan
  • /speckit.tasks
  • /speckit.implement
  • /speckit.converge

Skips the constitution and all three gates. Good for a well-understood change in a codebase you know.

Full path

Production features

  • /speckit.constitution then /speckit.specify
  • /speckit.clarify — resolve ambiguity
  • /speckit.plan then /speckit.checklist
  • /speckit.tasks then /speckit.analyze
  • /speckit.implement then /speckit.converge

Every artifact is reviewed before the next step consumes it. Use it when the cost of building the wrong thing is high.

XIV. Commands · Set the rules, state the goal 19

constitution & specify.

# Once per project /speckit.constitution This project is security-first. All user input is validated at the boundary. We use TDD strictly. Prefer standard library over new dependencies. # Once per feature /speckit.specify Build a photo organizer where albums are grouped by date and can be reordered by drag and drop on the main page. Albums are never nested. Inside an album, photos are previewed as tiles.
constitution · the guardrails

Writes .specify/memory/constitution.md and keeps the dependent templates in sync. Every later phase is evaluated against it, so this is where testing standards, security rules, and architectural limits belong.

specify · the goal

Creates or updates spec.md from a natural-language description. Describe user-facing behaviour and outcomes.

Common mistake

Naming your stack here. "Use Postgres and React" belongs in /speckit.plan. Putting it in the spec locks in a design decision before anyone has agreed on the requirement.

Rule of thumb

If a sentence would still be true after switching languages, it belongs in the spec.

XV. Commands · Remove doubt, choose the stack 20

clarify, plan & checklist.

# Focus one area at a time; repeat /speckit.clarify Focus on the task card: status changes, comment limits, and who can be assigned. # Now the technical decisions /speckit.plan Use .NET Aspire with Postgres. Blazor Server frontend with drag-and-drop and real-time updates. REST APIs for projects, tasks, and notifications. # Broad pass, or focused /speckit.checklist /speckit.checklist Focus on board interactions and comment permissions.
clarify

Asks up to five targeted questions and folds your answers back into spec.md. Run it as many times as you need, taking a different area each time. Clarifying first stops you designing on top of an assumption.

plan

Generates plan.md and the supporting design artifacts from the spec. Pass your stack, architecture, and technical constraints as arguments — this is the one step where implementation detail is wanted.

checklist

Produces a checklist that tests the requirements, not the code: "Are drag-and-drop rules defined for every column?", "What happens when an assigned user is deleted?" If it finds gaps, go back and tighten the spec.

XVI. Commands · Break it down, check it 21

tasks & analyze.

# No arguments needed /speckit.tasks # tasks.md comes out phased: # Setup # Foundational (blocking work) # User story 1 (highest priority) # User story 2 ... # Polish (cross-cutting) # Read-only consistency check /speckit.analyze # Convert the list into GitHub issues /speckit.taskstoissues
tasks

Turns the design artifacts into an actionable, dependency-ordered tasks.md. Tests are generated inside a user story's phase when you asked for them, and tasks that can run in parallel are marked as such.

analyze

Cross-checks spec.md, plan.md, and tasks.md against each other — a task with no matching requirement, a plan choice that contradicts the spec. It only reports; it never edits. Re-run until it comes back clean.

taskstoissues

Optional. Converts the task list into GitHub issues so work can be tracked and distributed. It relies on MCP, so an agent without MCP support cannot run it as intended.

XVII. Commands · Build and close out 22

implement & converge.

# Small feature — build it all /speckit.implement # Large feature — one stage at a time /speckit.implement Only the Setup and Foundational phases: scaffolding plus the data model with basic CRUD. Stop before the user stories. /speckit.implement Now the Kanban board story: drag and drop between columns. # Did anything get missed? /speckit.converge
implement

Executes tasks.md in dependency order. For anything large, scope each run with an argument and verify the result before continuing — this keeps the agent's context focused and the diffs reviewable.

converge

Assesses the codebase against the spec, plan, and tasks. Append-only — it never edits or deletes code, and its only possible write is adding tasks. Run it only after implement has run on the current task list.

Two outcomes

Converged — no gaps, tasks.md untouched, move on to review or a pull request. Tasks appended — gaps were found and added under a Convergence section; run implement again, then converge again. Each pass finds fewer items.

XVIII. Agents · Integrations 24

30+ supported agents.

An integration is the adapter between Spec Kit and one coding agent. These are the keys you pass to --integration.

copilot claude gemini codex cursor-agent amp agy auggie bob cline codebuddy devin droid firebender forge goose grok hermes junie kilocode kimi kiro-cli lingma omp opencode pi qodercli qwen rovodev shai tabnine trae vibe zcode zed generic

The invocation differs

Most agents expose /speckit.command. Skills-based agents use /speckit-command; Codex and ZCode use $speckit-command; Kimi uses /skill:speckit-command.

CLI or IDE

CLI agents must be installed on your machine. IDE agents work through the editor. specify integration list shows which is which.

Bring your own

For an agent that is not listed, use --integration generic --integration-options="--commands-dir <path>".

XIX. Agents · GitHub Copilot 25

The Copilot integration.

# Default — legacy markdown mode specify init my-project --integration copilot # .github/agents/*.agent.md # .github/prompts/*.prompt.md # .vscode/settings.json (merged) # Recommended — agent skills mode specify init my-project --integration copilot \ --integration-options="--skills" # .github/skills/speckit-specify/SKILL.md # invoked as /speckit-specify # Move an existing project across specify integration upgrade copilot \ --integration-options="--skills"
Two layouts

Copilot still defaults to legacy markdown mode, which writes agent files and companion prompt files and merges a VS Code settings block. That default is deprecated and will change in a future release.

Skills mode

Passing --skills scaffolds one skill folder per command under .github/skills/, invoked as /speckit-specify, /speckit-plan, and so on. Install warns if you leave it off.

Non-interactive default

If --integration is omitted in CI or a piped run, Spec Kit picks copilot.

Watch out

Changing between command and skills layouts is blocked while preset artifacts are registered. Remove the presets, upgrade, then reinstall them.

XXI. Extensibility · Make it yours 27

Extensions, presets, bundles.

Add capabilities, change how existing ones behave, or install a whole role's setup at once.

Extensions — add capability

New commands, phases, and tool integrations. specify extension search then add <name>. The bundled git extension restores branch workflows; bug adds assess, fix, and validate triage under .specify/bugs/.

Presets — change behaviour

Override the templates that core and extensions ship, without adding anything new: a compliance spec format, your own terminology, mandatory security gates, test-first task ordering. Stackable with priority.

Bundles — a role in one command

A versioned manifest that pins a curated set of extensions, presets, workflows, and steps. specify bundle info shows exactly what install will add. Examples ship for PM, BA, security researcher, developer.

Template resolution — first match wins, top down

1 · Project overrides .specify/templates/overrides/ 2 · Presets 3 · Extensions 4 · Spec Kit core

Also · specify workflow chains commands, prompts, shell steps, and human checkpoints into a resumable sequence

XXII. Practices · Getting value from it 28

Habits that make it work.

The commands are the easy part. These are the habits that decide whether the process actually pays off.

Read every artifact before moving on

A spec you skimmed becomes a plan you did not agree to, then tasks nobody asked for. Two minutes at each checkpoint saves the whole run.

Keep the stack out of the spec

Requirements stay true across languages and frameworks. If a sentence names a library, it belongs in the plan instead.

Fix problems at their source

When analyze flags a mismatch, do not patch tasks.md by hand. Correct the spec or the plan and regenerate.

Implement in stages

Scope each /speckit.implement run to a phase or a user story, verify it, then continue. Whole-feature runs overload the agent's context.

Commit the artifacts

Check specs/ and .specify/ into version control. The spec is what reviewers should be reading alongside the diff.

Separate tooling and intent changes

On existing projects, refresh managed files when upgrading Spec Kit; change specs/ only when the intended behaviour changes.
