Ask the agent to create or review project artifacts. Run one step at a time and inspect its result before you continue.

/speckit-specify Describe what to build.

In GitHub Copilot's default skills mode, use the /speckit-… skills shown above. References may show dotted names such as /speckit.specify. Other agents can use $speckit-… or /skill:speckit-…. Use the form your agent exposes; do not enter agent skills in the terminal.

The files are generated in the project. The agent reads them as context for later steps.

Install the CLI. Initialize the project.

Quickstart route: PyPI + uv

●Terminal
# Install the CLI
$ uv tool install specify-cli

# Confirm the CLI is available
$ specify version

# Create a project for GitHub Copilot
$ specify init my-project --integration copilot
$ cd my-project

Before you start

  • Python 3.11 or newer
  • uv is the recommended package manager
  • A supported AI coding agent
  • Linux, macOS, or Windows

Other supported installs include pipx install specify-cli and pip install specify-cli. For a pinned source release, see the official install guide.

Run the coding agent from my-project. For an existing repository, read the existing-project guide before you initialize it. Git is only needed for Git workflows added by the opt-in git extension.

The SDD flow, from intent to checked work.

Core process · per feature

/speckit-constitutionSet project principles once. Update them when the principles change.
  1. START HERE/speckit-specify
  2. OPTIONAL GATE/speckit-clarify
  3. CORE STEP/speckit-plan
  4. OPTIONAL GATE/speckit-checklist
  5. CORE STEP/speckit-tasks
  6. OPTIONAL GATE/speckit-analyze
  7. CORE STEP/speckit-implement
  8. CORE STEP/speckit-converge
↻ If gaps remainConverge appends tasks. Implement those tasks, then converge again until the result is Converged.

Only /speckit-specify is strictly required before /speckit-plan. Add the dashed gates when ambiguity or risk makes them useful.

Know what each SDD step changes.

Core command reference

SkillPurpose and outputUse it when
/speckit-specifyDefine user needs, behaviour, and scope in spec.md. Keep implementation choices out.Starting or changing a feature
/speckit-planChoose the technology, architecture, and technical constraints in the plan.The requirements are clear enough to design
/speckit-tasksCreate dependency-ordered work in tasks.md.The plan is ready to build
/speckit-implementExecute the tasks. Large changes can be run one phase or user story at a time.Tasks are ready and reviewed
/speckit-convergeCompare implementation with the spec, plan, and tasks. Append any gaps to the task list.After implementation; repeat if tasks were added

/speckit-constitution sets project-wide principles. It is not a per-feature spec or a technology plan.

Add a gate only when it answers a real question.

Optional checks

/speckit-clarify

Use before planning when requirements are unclear. It asks up to five focused questions and updates the spec with your answers.

/speckit-checklist

Use to check whether requirements are complete, clear, and consistent. This reviews requirements; it does not test the implementation.

/speckit-analyze

Use after tasks and before implementation to find conflicts or gaps across the spec, plan, and tasks. It reports findings; it does not edit them.

For a small, clear feature, use the shorter path. For production work, unclear requirements, or costly changes, add the gates that reduce the risk.

Fix a bug without starting an SDD feature.

Opt-in bug extension

●Terminal · project root
$ specify extension add bug
01 · ASSESS/speckit-bug-assess
02 · FIX/speckit-bug-fix
03 · TEST/speckit-bug-test

Keep each report with the bug.

Each command uses the same slug. Its reports are saved under .specify/bugs/<slug>/.

  • Assess Read-only triage and proposed fix
  • Fix The only bug step that edits source code
  • Test Read-only verification report

The final verdict is verified, partial, or failed. Only verified confirms the fix.

Start assess with a report and slug, for example: /speckit-bug-assess "Login fails" slug=login-fails. Reuse slug=login-fails for fix and test.

Test an idea before you commit to building it.

Opt-in assess extension

●Terminal · initialized project
$ specify extension add assess
01/speckit-assess-intake
02/speckit-assess-research
03/speckit-assess-define
04/speckit-assess-shape
05/speckit-assess-decide

Assessment is a decision record.

It can run without source code. It writes evidence and a decision under .specify/assessments/<slug>/; it does not start implementation.

  • go Continue if you choose to
  • needs-clarification Resolve named unknowns
  • kill Record why you stop

A go decision can include a handoff to /speckit-specify. It does not force that next step.

Start intake with an idea and slug, for example: /speckit-assess-intake "Support offline work" slug=offline-mode. Reuse slug=offline-mode for later stages.

For GitHub issues, install the optional extension with specify extension add github, then use /speckit-github-taskstoissues. It needs a GitHub origin and GitHub MCP access. The core /speckit-taskstoissues command is deprecated.

Keep the work clear and reviewable.

Before · during · after

Before you initialize an existing repository

Read the existing-project guide. Review your working tree, and commit or back up local changes first. Use --here to target the current directory. Use --force only when you accept the merge or overwrite warning.

When you upgrade

Updating the CLI does not update project files. Use specify integration upgrade <key> for agent files and specify extension update for installed extensions. Repeat integration upgrade for each installed key; review local edits before using --force.

To check for a newer CLI release, specify self check is read-only. specify self upgrade changes the installed CLI.

Running uv tool install specify-cli again does not upgrade an existing install.

  1. Review each result. Correct a spec or plan before generating more work.
  2. Keep the spec about user needs. Put technology choices in the plan.
  3. Implement in stages. Scope large runs, then verify each stage.
  4. Keep the artifacts with the code. Review specs and plans with the implementation.
