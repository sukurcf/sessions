III. Motivation 04

Why migrate Python 2.

Python 2 reached end-of-life on January 1, 2020. No security patches, no bug fixes, no community support — running Python 2 in production is a ticking time bomb.

No security patches

CVEs discovered after 2020 are never fixed. Your app is permanently vulnerable.

Libraries dropping support

NumPy, Django, Flask, requests — all major libraries have dropped Python 2 support.

Modern Python features

f-strings, type hints, async/await, walrus operator, pattern matching — all Python 3 only.

Source: python.org/doc/sunset-python-2

V. Cloud agent 06

Meet the Cloud Agent.

GitHub Copilot's coding agent is an autonomous AI developer that works directly on GitHub.com — it takes on issues, writes code, runs tests, and opens PRs.

Issue-driven workflow

Assign any GitHub issue to @copilot. The agent reads the issue, plans the work, and starts coding autonomously.

Secure cloud environment

Runs in an ephemeral VM using GitHub Actions runners. Clones the repo, creates a branch, and works in complete isolation.

Self-correcting

Runs builds and tests, analyzes failures, iterates on fixes until CI passes — all without human intervention.

Draft PR with full history

Opens a draft PR with incremental commits, detailed description, and session logs for full transparency.

VII. Spec-Kit 08

What is Spec-Kit.

Spec-Kit is GitHub's open-source toolkit for spec-driven development. Instead of prompts, you write structured specifications — the AI agent follows them to generate, test, and validate code.

Specs as source of truth

Specifications define what the system should do, why, and for whom. Both humans and AI agents use them to generate code.

Works with existing code

Run specify init . in your repo root to add Spec-Kit to an existing Python 2 codebase. Your code stays untouched.

Agent-agnostic

Works with GitHub Copilot, Claude Code, Gemini CLI, and other AI coding agents. Pick your integration during init.

Living documentation

Specs update as requirements change. They become the behavioral contract for migration validation.

Source: github.com/github/spec-kit

Resolve ambiguities: "Should we keep Python 2 compatibility with six? Or target Python 3.10+ only?" The agent asks follow-up questions.

XI. Custom agents 12

Custom agents.

Define specialized AI agents in your repo using .agent.md files. Each agent has a specific persona, tools, and instructions — like hiring specialists for your migration team.

YAML frontmatter + markdown

Each .agent.md file has YAML metadata (name, description, tools, model) followed by markdown instructions for the agent's behavior.

Placed in .github/agents/

Files in .github/agents/ are available repo-wide. The cloud agent discovers and uses them when relevant to the task.

Tool restrictions

Control what each agent can do: read-only analysis, file edits, shell access, or specific MCP server connections.

Model selection

Assign the best model per agent: premium models for complex migration logic, lighter models for documentation tasks.

Source: docs.github.com/copilot/reference/custom-agents-configuration

XVIII. Instructions file 19

Migration instructions file.

This file tells both the cloud agent and local Copilot how to behave during the Python 2→3 migration.

# .github/copilot-instructions.md

## Migration context
We are migrating from Python 2.7 to Python 3.10+.
Target: idiomatic Python 3 with type hints.

## Rules
- Replace print statements → print() function
- Replace % formatting → f-strings
- Replace dict.has_key() → in operator
- Replace raw_input() → input()
- Replace xrange() → range()
- Use pathlib instead of os.path
- Add type hints to all function signatures
- Test framework: pytest
- Never use the six compatibility library

Source: docs.github.com/copilot/customizing-copilot/adding-repository-custom-instructions

XIX. Best practices 20

Migration best practices.

Hard-won lessons for a successful Python 2→3 migration with Copilot cloud agent.

Spec first, code second

Use Spec-Kit to document Python 2 behavior before converting. Specs become your behavioral contract for validation.

One module per issue

Create focused GitHub issues — one module per migration task. The cloud agent works best with bounded, well-scoped work.

Write tests before migrating

Use the test agent to generate pytest tests against the Python 2 code. Run the same tests against Python 3 output.

Set up CI for both versions

During migration, run CI with tox on Python 2.7 and 3.10+. Ensure behavior parity before dropping Python 2.

Review every PR

The cloud agent is your assistant, not your autopilot. Always verify encoding changes, integer division, and string handling.

Use custom agents for consistency

Define migration rules once in .agent.md files. Every cloud agent session follows the same patterns across all modules.
