I. GitHub Enterprise and workflows 06

Three levels, one policy chain.

An enterprise account gives centralised administration over many organisations. Policy set at the top can be enforced downward; it cannot be loosened from below.

Level 1

Enterprise account

Billing, identity, security policy, audit log, and enterprise-wide rulesets. One per company or per division.

Level 2

Organization

Teams, membership, organization rulesets, custom properties, required workflows, and repository defaults.

Level 3

Repository

Code, branches, repository rulesets, CODEOWNERS, environments, secrets, and Actions workflows.

When it matters. A division-wide requirement — every production deployment needs two reviewers — belongs at the enterprise or organization level as a ruleset. Putting it in each repository means it will drift.

Source: docs.github.com/en/enterprise-cloud@latest/admin/concepts/enterprise-fundamentals/enterprise-accounts · August 2026

I. GitHub Enterprise and workflows 08

Who signs in, and how.

This is the single decision that is hardest to reverse. Pick it before you migrate repositories.

Enterprise Managed Users

GitHub creates and owns the account. It is provisioned from your identity provider over SAML or OpenID Connect plus SCIM, and it can only access enterprise resources.

Full lifecycle control No public contributions Deprovision on leaver

Personal accounts with SAML single sign-on

Developers keep their own github.com account and authenticate through your identity provider to reach enterprise resources.

Open source contribution One identity across employers Weaker offboarding

The trade. Managed users give you deterministic offboarding and a clean audit trail. They also block a developer from contributing to a public project from that account. Teams that publish open source usually run both models in separate enterprises.

I. GitHub Enterprise and workflows 09

Governance you configure once.

Repository rulesets

Named rules that target branches and tags by pattern, support bypass lists, and can be layered. They replace classic branch protection.

Organization rulesets

The same rules applied across many repositories at once, so a new repository is compliant on the day it is created.

CODEOWNERS

Maps file paths to the teams that must review changes to them. Combine with a ruleset that requires code owner approval.

Custom properties

Structured metadata on repositories, such as criticality or product line. Rulesets can target repositories by property value.

Required workflows

Organization-level workflows that run on every pull request and push in the repositories you select.

IP allow lists

Restrict access to enterprise resources to network ranges you control.

SCIM provisioning

Creates, updates, and deactivates accounts from your identity provider so access follows the joiner-mover-leaver process.

Audit log streaming

Continuous export of audit and Git events to Amazon S3, Azure Blob Storage, Azure Event Hubs, Google Cloud Storage, Datadog, Microsoft Purview, or Splunk.

GitHub Packages

Registries for container images and language packages, with access controlled by the same repository permissions.

Source: docs.github.com/en/enterprise-cloud@latest/admin/monitoring-activity-in-your-enterprise · August 2026

I. GitHub Enterprise and workflows 10

Anatomy of a workflow.

.github/workflows/ci.yml

name: Learn GitHub Actions
on: [push]

jobs:
  check-bats-version:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v7
        with:
          node-version: '14'
      - run: npm install -g bats
      - run: bats -v

Verbatim from the GitHub Actions workflow syntax reference.

Where it lives

Any .yml or .yaml file under .github/workflows/. There is no registration step; committing the file is the deployment.

on

The trigger. Common values are push, pull_request, schedule, workflow_dispatch, and workflow_call.

jobs and runs-on

Each job gets a fresh virtual machine. ubuntu-latest currently maps to Ubuntu 24.04 with 2 processors and 8 GB of memory.

uses versus run

uses calls a published action. run executes a shell command. A step is one or the other, never both.

needs and strategy

needs: [build] orders jobs. strategy.matrix expands one job definition into many parallel runs.

Source: docs.github.com/en/actions/using-workflows/workflow-syntax-for-github-actions · August 2026

I. GitHub Enterprise and workflows 12

Stop copying pipelines.

Reusable workflow — the callee

on:
  workflow_call:
    inputs:
      node-version:
        required: true
        type: string

The caller

jobs:
  build:
    uses: siemens/ci/.github/workflows/node.yml@v1
    with:
      node-version: '20'

Reusable workflow

A whole workflow with its own jobs, called from another workflow with jobs.<id>.uses. Each called job gets its own runner.

Composite action

A bundle of steps that runs inside an existing job on the same runner. Use it when you are packaging steps, not jobs.

Pick reusable workflows when

The unit you want to share is a complete pipeline stage with its own runner, permissions, and environment.

Pick composite actions when

The unit is three or four steps that always appear together, such as authenticate, restore cache, install dependencies.

Version them

Publish shared workflows from a central repository and reference them by tag, so a change to the shared pipeline is a deliberate upgrade.

Source: docs.github.com/en/actions/using-workflows/reusing-workflows · August 2026

I. GitHub Enterprise and workflows 13

Deploy without stored credentials.

Environment plus federated identity

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    permissions:
      id-token: write   # mint the OIDC token
      contents: read
    steps:
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUB_ID }}

No cloud password or long-lived key is stored in GitHub.

Environments

A named deployment target — staging, production — that carries its own secrets and variables and its own protection rules.

Protection rules

Required reviewers, up to six of them, a wait timer, and a restriction on which branches or tags may deploy.

Environment secrets

Only readable by a job that declares that environment, and only after every protection rule has passed.

OpenID Connect

The job requests a short-lived signed token from GitHub. Your cloud provider validates it and issues a temporary access token scoped to that repository and branch.

Why it matters here

A leaked workflow log can no longer expose a reusable cloud credential, because there is no reusable cloud credential.

Source: docs.github.com/en/actions/deployment/security-hardening-your-deployments/about-security-hardening-with-openid-connect · August 2026

I. GitHub Enterprise and workflows 14

Five rules for hardening Actions.

Least privilege by default

permissions:
  contents: read

# pin third-party actions to a commit
- uses: actions/checkout@e9e28dc...

# never interpolate untrusted input
- env:
    TITLE: ${{ github.event.issue.title }}
  run: echo "$TITLE"

1 · Pin to a commit

Reference third-party actions by full commit hash, not by tag. A tag can be moved to point at new code.

2 · Restrict the token

The automatic GITHUB_TOKEN should start at contents: read and be raised only where a job genuinely writes.

3 · Never inline untrusted text

Issue titles, branch names, and pull request bodies are attacker-controlled. Pass them through an environment variable, never straight into a shell line.

4 · Treat pull_request_target carefully

It runs with repository secrets. Do not check out and execute code from a fork inside it.

5 · Use federated identity

Replace stored cloud keys with OpenID Connect so there is nothing durable to steal.

Source: docs.github.com/en/actions/reference/security/secure-use · August 2026

II. Spec-driven development 17

The failure mode we are fixing.

An agent handed a one-line request will fill every gap with an assumption. It will not tell you which assumptions it made, and the assumptions arrive as committed code.

Prompt only

"Add date range filtering to the report page."

The agent silently decides: whether start and end may be the same day, whether the range is inclusive, which time zone applies, what happens when the range is empty, and whether the filter is stored in the URL.

You discover each decision during review, one comment at a time.

Specification first

The same request, written down

Every one of those questions is answered in a file before implementation starts. The agent has nothing left to guess, and the review is about code rather than intent.

When the agent does the wrong thing, the specification tells you whether the agent was wrong or the specification was.

For regulated work. A written specification, reviewed and committed alongside the change, is also the artefact your process auditors ask for. The agent workflow and the compliance workflow want the same document.

II. Spec-driven development 18

Four artefacts, in order.

01

Constitution

The rules that hold for every feature in this repository: language, testing standard, architectural constraints, what is never allowed.

02

Specification

What this one feature must do, in user-visible terms. Requirements and acceptance criteria. No technology choices.

03

Plan

How it will be built. Stack, data model, interfaces, and the parts of the existing system that will change.

04

Tasks

An ordered, individually verifiable task list. This is the unit the agent executes and the unit you review progress against.

The rule that makes it work. Each artefact is reviewed by a person before the next one is generated. The value is not in the documents; it is in the four review gates they create before any code exists.

Source: github.com/github/spec-kit · August 2026

II. Spec-driven development 19

Spec Kit in three commands.

Install and initialise

# install the CLI
uv tool install specify-cli

# scaffold a project for GitHub Copilot
specify init my-project --integration copilot

# see every supported agent

Commands verbatim from the Spec Kit README. Current release 0.15.2.

What Spec Kit is

An open-source toolkit published by GitHub that installs a set of slash commands and templates into your repository, then drives your existing coding agent through them.

It is not a model

Spec Kit does not run inference. It shapes the prompts and the files your agent works from, so you keep the model and the tooling you already use.

Agent coverage

More than thirty-five integrations, including GitHub Copilot, Claude Code, Codex CLI, Cursor, Gemini CLI, Cline, and Zed.

Everything is committed

The templates, the constitution, and every specification live in the repository and go through pull request review like any other file.

II. Spec-driven development 22

The constitution.

.specify/memory/constitution.md

## Language and runtime
Services are C++20 or TypeScript.
No new Python services.

## Testing
Every public function needs a unit test.
Integration tests run against a container,
never a shared environment.

## Never
- No direct database access from handlers
- No new third-party dependency without
  an entry in docs/adr/

What belongs here

Constraints that are true for every feature. If a rule only applies to one feature, it belongs in that feature's specification instead.

Write the prohibitions

Agents follow negative constraints well. A short list of things that are never acceptable is more effective than a long description of good style.

Keep it short

Every command reads this file on every run. A long constitution costs tokens on every single interaction and dilutes the rules that matter.

Treat it as code

Change it through a pull request with the team that has to live under it. It is a standards document that happens to be machine-readable.

Source: github.com/github/spec-kit README · August 2026. Example content is illustrative.

II. Spec-driven development 23

Four modes, four jobs.

Read only

Ask

Answers a question about the code. Changes nothing. Use it to understand an unfamiliar module before you touch it.

Narrow

Edit

Applies a change to files you have selected. You control the blast radius by choosing the files.

Think first

Plan

Asks clarifying questions about edge cases and requirements, then produces a plan. Writes no code.

Autonomous

Agent

Chooses its own files, runs commands, reads results, and iterates until the task is done.

The mistake to avoid. Reaching for agent mode on an ambiguous task. The mode that decides the most should be given the least ambiguity. Ambiguous work goes to plan mode first.

Source: github.blog/ai-and-ml/github-copilot/the-harness-is-all-you-need-mostly · July 2026

II. Spec-driven development 24

Plan mode to agent mode.

In the chat panel

/plan Build a date picker component.
The user should be able to move between
years, months, and days.

# Copilot replies with questions:
#  Can start and end date be the same?
#  Are partial selections valid?
#  What is the minimum year?

# answer them, review the plan,
# then switch to agent mode

Example prompt and questions from the GitHub engineering blog.

1 · State the outcome

Describe what the user should be able to do. Do not describe the implementation; plan mode will propose one.

2 · Answer the questions

This is the step people skip. Each unanswered question becomes an assumption in the code you have to find later.

3 · Edit the plan directly

The plan is text. Correct it yourself rather than negotiating with the model over several turns — it is faster and it costs nothing.

4 · Hand it to agent mode

Agent mode now starts with an approved plan instead of a sentence, so it spends its work on implementation rather than on guessing.

Where it also runs

The GitHub Copilot app exposes the same idea as session modes: Interactive, Plan, and Autopilot.

Source: github.blog/ai-and-ml/github-copilot/the-harness-is-all-you-need-mostly · July 2026

II. Spec-driven development 25

Four controls on an agent.

A specification is the first control. It is not the only one, and it does not replace the others.

1 · Bound the intent

The specification and the constitution define what is in scope. Anything the agent proposes that is not in the specification is, by definition, scope creep you can point at.

2 · Bound the tools

A custom agent declares which tools it may use. A review agent that cannot write files cannot accidentally rewrite your branch.

3 · Bound the merge

Agent output arrives as a pull request. Rulesets, required checks, and CODEOWNERS apply to it exactly as they apply to a person.

4 · Bound the runtime

Hooks run your own shell commands before and after every tool call, so you can block a command, log it, or require an approval.

The point. None of these controls depend on the model behaving well. They are the same controls you already apply to a new engineer: an agreed scope, limited permissions, a review before merge, and an audit trail.

III. House rules 28

Six files, six jobs.

These are not alternatives to each other. Each one answers a different question, and a mature repository has several of them.

copilot-instructions.md

Always loaded. The handful of rules that apply to every request in this repository.

*.instructions.md

Loaded by path. Rules that only apply to files matching a glob, such as your test directory or your API layer.

AGENTS.md

Portable. How to build, test, and run this project. Read by GitHub Copilot and by other vendors' agents.

SKILL.md

Loaded on demand. A procedure the agent pulls in only when the task matches its description.

*.agent.md

Chosen by you. A named agent with its own instructions, its own tool list, and its own model.

hooks/*.json

Runs your code. Shell commands at defined points in the agent's lifecycle. Not advice — enforcement.

The cost model. Always-loaded files are paid for on every request. On-demand files are paid for only when used. This is why a long copilot-instructions.md is expensive and a long skill is not.

III. House rules 29

The file every request reads.

.github/copilot-instructions.md

This is a C++20 telemetry service built
with CMake and tested with GoogleTest.

- Build with `cmake --preset ci`
- Run tests with `ctest --preset ci`
- Error handling uses `std::expected`,
  never exceptions across a module edge
- Log through `tel::log`, never `printf`
- Public headers live in `include/tel/`
  and must compile standalone

Plain Markdown. No frontmatter required.

Where it goes

.github/copilot-instructions.md at the repository root. It is read on every GitHub Copilot request in that repository.

Keep it under two pages

GitHub's own guidance: short, self-contained, no references to external resources.

What to leave out

Style preferences your formatter already enforces, instructions about response length, and anything a linter would catch. They waste context on every request.

What earns its place

The build command, the test command, the two or three architectural rules a newcomer always gets wrong, and the things that are never allowed.

Pull request behaviour

When GitHub Copilot reviews a pull request it reads instructions from the head branch, so you can test a change to this file in the pull request that introduces it.

Source: docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions · August 2026

III. House rules 30

Rules that apply to some paths.

.github/instructions/tests.instructions.md

---
applyTo: "**/*.test.ts,**/*.spec.ts"
---

Tests use Vitest, never Jest.

One behaviour per test. The test name
states the behaviour, not the function
name.

Do not mock the module under test. Mock
only at the network and filesystem edge.

Where it goes

Any file matching .github/instructions/**/*.instructions.md.

applyTo

A glob, or a comma-separated list of globs, in the YAML frontmatter. The file is loaded only when a matching file is in play.

Why this beats one big file

Your testing conventions do not need to be in context while someone edits a build script. Splitting by path keeps each request cheaper and more focused.

Good candidates

Tests, database migrations, public API surfaces, generated code that must not be edited by hand, and anything with a regulatory constraint attached.

Start here

If you write only one of these, write the one for your test directory. It is where inconsistent agent output is most visible.

III. House rules 31

One file every agent reads.

AGENTS.md

# Telemetry service

## Dev environment
Requires CMake 3.28 and Ninja.
`./scripts/bootstrap.sh` installs both.

## Build
`cmake --preset ci && cmake --build --preset ci`

## Test
`ctest --preset ci --output-on-failure`

## Pull requests
Title format: `[TEL] <summary>`
Run clang-format before pushing.

What it is

An open standard, stewarded by the Agentic AI Foundation under the Linux Foundation, and used by more than sixty thousand open-source projects.

No schema

It is plain Markdown. There are no required sections. The convention is development environment, build, test, and pull request guidance.

It nests

Put one at the repository root and another inside a subdirectory. The nearest file in the directory tree wins, which suits a monorepo.

It is portable

GitHub Copilot reads it, and so do Cursor, Windsurf, Gemini CLI, Zed, and others. CLAUDE.md and GEMINI.md are recognised the same way.

Why that matters at Siemens

Teams that use different tools can still share one description of how a repository is built and tested, instead of maintaining one file per vendor.

III. House rules 32

When two files disagree.

Instructions combine rather than replace each other. Where they genuinely conflict, this is the order.

Priority Source What belongs there
HighestPersonal instructionsYour own preferences, applied across every repository you work in.

3.github/copilot-instructions.mdRepository-wide rules.

The practical rule

Do not restate an organization rule in a repository file. Duplication is where the two copies start to drift apart.

Nested AGENTS.md

Where they go

.github/skills/NAME/SKILL.md for a repository, or ~/.copilot/skills/NAME/SKILL.md for yourself. The directory name must match the name field.

How one gets loaded

GitHub Copilot matches your request against the description field. That sentence is the whole retrieval mechanism, so write it as a trigger condition, not as a summary.

allowed-tools

An optional frontmatter field that pre-approves specific tools, such as shell, so the skill runs without a confirmation prompt.

Where they work

The cloud agent, Copilot code review, the GitHub Copilot CLI, the GitHub Copilot app, and agent mode in Visual Studio Code and JetBrains IDEs.

Good first skills

IV. Model selection and cost 47

Cached input costs one tenth.

The largest number on your invoice is input tokens, and most of them are the same tokens re-sent every turn. When they hit the cache they are billed at roughly ten percent. Three ordinary habits destroy that cache.

Destroys the cache

Switching model mid-session

The new model has never seen the conversation. Everything is re-sent as fresh input, at ten times the cached rate.

Destroys the cache

Resuming an old session

The cache expires — around twenty-four hours for OpenAI models and about an hour for the others. Yesterday's session restarts at full price.

Destroys the cache

Changing reasoning settings

Altering the reasoning level part-way through invalidates what was cached before it.

The working rule. Choose the model before the first message, finish the task in one sitting, and start a new session for the next problem rather than continuing an old one. Continuing costs more than starting over, and it produces worse answers.

Source: docs.github.com/en/copilot/tutorials/optimize-ai-usage · August 2026

IV. Model selection and cost 48

Eight habits that cut the bill.

1 · New problem, new session

Switching topic inside an old session means paying to re-send everything irrelevant, on every turn.

2 · Compact long sessions

Use /compact to replace a long history with a summary before you continue.

3 · Point at files

A direct file reference is far cheaper than an agent searching the repository to find it.

4 · Give a project map

A short description of the layout in your instructions file removes an entire exploration phase from every session.

5 · Enable only the tools you need

Every enabled toolset adds its description to every request, whether or not it is used.

6 · State the stopping condition

"Stop when the tests pass" ends the loop. Without it the agent keeps improving and keeps charging.

7 · Delegate investigation

Send exploration to a subagent on a fast model. The parent session receives the conclusion, not the twenty files.

8 · Do not switch model mid-task

Decide first. Switching restarts the cache from zero.

Measure before you optimise. The GitHub Copilot CLI has a /usage command and organizations get consumption reporting. Two weeks of measurement will tell you which of these eight applies to your team, and it is rarely the one people expect.

Source: docs.github.com/en/copilot/tutorials/optimize-ai-usage · August 2026

Secret Protection.

Secret scanning

Detects credentials across the whole repository history, not only the current commit. A key deleted three years ago is still a key that was published.

Push protection

Blocks the push before the secret reaches the repository. This is the control that matters; everything else is cleanup.

Validity checks

Asks the issuing service whether a detected credential is still active, so triage starts with the ones that are.

Delegated bypass

Named people or teams approve bypass requests. Trusted actors can be exempted; other requests expire after seven days.

What it costs

Free on all public repositories. For private and internal repositories it requires the GitHub Secret Protection product, listed at 19 US dollars per active committer per month.

An active committer is a unique person who has committed to any covered repository in the last ninety days, so the figure tracks people who write code rather than seats.

Turn on push protection first. Historical scanning produces a backlog that needs rotation work. Push protection stops the backlog from growing while you work through it. Enable both, but sequence the effort in that order.

From alerts to campaigns.

Every large organisation reaches the same point: thousands of alerts, and no agreement about which ones get fixed this quarter. These two features exist for that moment.

Security overview

One view across the organization, with separate lenses for risk, coverage, assessments, campaigns, enablement, CodeQL pull requests, Dependabot, and secret scanning.

Coverage is the view to open first. It tells you which repositories have no scanning at all, and that is almost always where the real exposure is.

Group a set of related alerts into one piece of work with an owner and a deadline. Campaigns support automatic autofix suggestions, and an alert can be assigned to a person or to the cloud agent.

Cover the uncovered branch, not the

Why a custom agent

The tools list is what stops it editing production code to make a test pass. That is a real failure mode, and an instruction alone does not prevent it.

Why a fast model

Writing a test for an existing function is well-scoped work. This is the highest-volume, lowest-complexity task in the module, so it belongs on the cheapest tier.

Give it a target

Point it at one module and one coverage report. An agent told to "improve coverage" across a whole service will write many shallow tests.

Scale it with the cloud agent

Open one issue per module, assign each to the cloud agent, and review the resulting pull requests. Sessions run up to fifty-nine minutes each.

Guard the metric

Coverage rises whether or not the tests assert anything useful. Review a sample by hand before you trust the number.
