I.Positioning03

What changes at the CLI.

GitHub Copilot CLI is terminal-native and agentic: it can inspect a repository, use tools, modify files, run commands, and work toward a requested result with approval boundaries.

II.Interactive CLI04

Start in the repository.

Launch from the directory whose files and commands should be in scope. Authenticate once, confirm directory trust, then ask for a concrete result.

# Install once
brew install --cask copilot-cli

# Start from the repository
cd path/to/repository
copilot

# First session
/login

First prompt

Give me an overview of this project, its test command, and the files that own authentication.

Use / for slash commands, ? for quick help, and Esc to cancel the current operation.

Source: docs.github.com/en/copilot/how-tos/copilot-cli/cli-getting-started · August 2026

III.Context input05

Send context from the terminal.

The working directory gives the session a starting point. Add only the files, issues, and commands needed for the current question.

# Include a file
@src/auth/login.ts

# Include a GitHub issue or PR
#42

# Run a local command directly
!git status

Three explicit inputs

@FILENAME includes file contents. #NUMBER includes a GitHub issue or pull request. !COMMAND runs a local shell command without asking the model to interpret it.

Keep the prompt specific. More context is not automatically better context.

IV.Model selection06

Choose the model.

Use Auto when you want GitHub Copilot CLI to select a model. Choose explicitly when the task needs a predictable model or a different speed and reasoning profile.

# Interactive selection
/model
/model auto
/model claude-sonnet-4.6

# Programmatic selection
copilot --model=gpt-5.3-codex

Scope the decision

Session: change the current run. Repo: pin a repository default. Global: set the default for future sessions.

A model change requested during a turn is queued and applied after that turn finishes.

V.Worked task07

One task, one repository.

Use a bounded requirement so each CLI step produces evidence for the next step.

Requirement

Add rate limiting to POST /login

Preserve existing status codes, make the window configurable, and avoid changing successful login behavior.

Acceptance checks

Behavior, tests, documentation

Burst requests are limited, the reset window is covered, the existing test suite passes, and the configuration is documented.

VI.Task to implementation08

Explore before edits.

Ask for ownership, constraints, and verification commands before asking the agent to modify files.

/ask What files own login and middleware?

Explore the repository. List the relevant files, current test commands, and constraints. Do not edit files.

Expected map

Route identifies the request entry point.

Middleware identifies the enforcement boundary.

Config identifies the safe control surface.

Tests identify the existing style and command.

VII.Task to implementation09

Plan the implementation.

Make the proposed file changes and verification steps visible before implementation begins.

/plan Add rate limiting to POST /login. Inspect the current auth flow, propose the smallest change, and list tests before editing.

/rubber-duck Check this plan for hidden behavior changes and missing tests.

Three useful boundaries

Plan mode explores and drafts without modifying project files.

Rubber duck gives a read-only second opinion on the plan.

Approval is the handoff from reasoning to implementation.

VIII.Task execution10

Implement with parallel work.

Split independent work only after the plan identifies clear file and test boundaries.

/fleet Implement the approved plan. One subtask updates middleware, one adds tests, and one updates the configuration documentation.

/tasks

Keep the coordinator visible

Parallel: independent subtasks run in separate contexts.

Coordinator: the main session tracks dependencies and integrates results.

Review: inspect each change before accepting the combined result.

IX.Task verification11

Run the test and fix loop.

Treat each test result as a new constraint. Keep the loop local and repeatable.

# Verify the repository
npm test

# Inspect the exact change
/diff

# Ask for a focused review
/review

Use failure evidence

Test fails: show the output and ask for the smallest correction.

Diff grows: ask which change is unnecessary.

Repeated failure: use /rubber-duck for an independent critique.

XIV.Inspect and ship16

Inspect and ship the delta.

Separate review of the change from the act of creating or fixing the pull request.

/diff
/review Focus on behavior regressions.
/security-review

/pr create
/pr fix
/delegate Finish the approved change and open a draft pull request.

Different checks, different commands

/diff shows the current or branch diff.

/review analyzes changes for code issues.

/security-review focuses on active local changes; it is not a full repository audit.

/pr create and /pr fix manage the current branch pull request.

/delegate hands the task to a remote repository workflow with an AI-generated pull request.

XV.Permissions and sandbox17

Keep approval boundaries explicit.

Use interactive approvals for normal work. Tighten permissions and sandbox access when the task or environment requires it.

/permissions show
/permissions assisted
/sandbox status
/sandbox policy

copilot --allow-tool='shell(git:*)' \
  --deny-tool='shell(git push)'

Use the smallest permission

Approval: allow one request, a location, or a session pattern.

Permissions: choose default, assisted, or allow-all mode intentionally.

Sandbox: inspect effective filesystem and network restrictions.

Startup: prefer --allow-tool, --deny-tool, and --add-dir over broad access.

XVI.Beyond interactive terminal18

Use the same task in automation.

Turn one bounded prompt into a non-interactive command after the interactive workflow is understood and its permissions are explicit.

copilot -p "Summarize failed tests and propose the smallest fix" \
  --model=claude-haiku-4.5 \
  --no-ask-user \
  --silent

Keep programmatic runs bounded

-p executes a prompt and exits. --silent returns only the agent response for clean scripting.

Grant only the tools, paths, and URLs the command needs. Redact sensitive environment values in captured output.

Prompt → context → plan → implement → test → review → ship
