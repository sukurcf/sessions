III. Build custom agents 04

How to create custom agents.

Use agent files for specialized personas like Security Reviewer, Release Manager, or Documentation Engineer.

Step 1 · Create file

Add .github/agents/<name>.agent.md in the repo. Use a clear name and narrow scope.

Step 2 · Define frontmatter

Set name, description, target, model list, and allowed tools so behavior is predictable.

Step 3 · Add workflow rules

Specify entry checks, output format, quality gates, and failure handling in plain language.

Step 4 · Invoke in chat

Call with @Security reviewer or your configured alias, then run against staged changes or file scopes.

# .github/agents/security-reviewer.agent.md
---
name: Security reviewer
description: "Find exploitable risks in changed code"
target: vscode
tools: [read, search, edit, execute]
---

Focus areas:
- Secrets, tokens, credentials
- Injection and unsafe command execution
- AuthN/AuthZ regressions
- Dependency and supply-chain risks

Output format:
1) severity 2) impacted file 3) exploit path 4) patch guidance
IV. Build custom skills 05

How to create custom skills.

Skills package reusable domain workflows so teams do not repeat prompt engineering in every session.

# folder structure
.github/skills/security-review/
├── SKILL.md
├── checklists/high-risk-paths.md
└── examples/false-positive-triage.md

# SKILL.md (core)
name: security-review
description: review changed code for exploitable issues
triggers: ["review", "security", "threat model"]
rules:
- prioritize exploitable findings
- include patch snippet and test advice

Design for triggerability

Add concise trigger phrases so the skill activates reliably when users ask in natural language.

Keep skills atomic

One skill = one operational outcome (review, migration, test triage) to avoid mixed behavior.

Version safely

Update examples/checklists as stack or policy evolves. Treat skills like code: review, test, iterate.

V. Lifecycle automation 06

How to use agent hooks.

Hooks run automation at key lifecycle points to enforce guardrails and reduce manual review noise.

Hook eventTypical automationOutcome
Session startLoad repo conventions and required filesConsistent agent context
Before tool usePolicy check on command/pathPrevents risky operations
After tool useParse output, redact sensitive dataCleaner and safer traces
Subagent endValidate result schemaStable downstream handoff
Session stopEmit summary and unresolved risksAudit-ready closure

Best practice

Keep hooks deterministic and fast. If a hook fails, log the reason and fail closed for high-risk actions.

Where to manage

Use the Agent Customizations UI in VS Code to inspect enabled hooks and debug execution order.

VI. Agent autonomy controls 07

Permission levels & Autopilot.

Tune execution autonomy per session to balance speed and governance.

Default approvals

Low-risk reads can proceed; risky writes/exec still ask for explicit approval.

Bypass approvals

Higher automation for trusted tasks and temporary execution windows.

Autopilot (Preview)

Auto-approves tools and clarifying prompts so the task can run to completion autonomously.

VII. Diagnostics in VS Code 08

Agent debug logs in VS Code.

Essential for understanding why an agent took an action, skipped a tool, or produced an unexpected answer.

What logs contain

Session IDs, prompts, tool invocations, model selection, hook events, MCP requests/responses, and structured error traces.

Where to view

Click the three-dot menu (⋯) in the top-right corner of Copilot Chat, then select "Open Agent Logs" to see the full session trace.

How it helps debugging

Pinpoints permission denials, malformed tool parameters, context truncation, and timing/race issues across subagents.

Operational pattern

Capture failing session ID, inspect tool timeline, reproduce minimal case, then fix instruction/skill/hook and re-run.

Tip: increase log verbosity temporarily during triage, then return to default to reduce noise.

IX. Code review governance 09

Customize code review with instructions.

Use repository instructions and skills to make review comments consistent with your architecture, security posture, and testing standards.

# .github/copilot-instructions.md (review excerpt)
When reviewing pull requests:
- prioritize exploitable security issues over style
- flag behavioral regressions with file-level evidence
- require tests for new branches and failure paths
- do not suggest broad refactors unrelated to change scope

Report format:
1. severity (high/medium/low)
2. file and impact
3. concrete fix suggestion

Layered customization

Use copilot-instructions.md for global behavior and skills for domain-specific checks.

MCP-backed context

Enrich reviews with internal policy docs, service ownership data, and ticket metadata where allowed.

Outcome

Higher signal review comments, fewer false positives, and better alignment with team standards.

X. Community resources 10

github/awesome-copilot.

Official community collection of agents, instructions, skills, hooks, workflows, and plugins — 34k+ stars, 400+ contributors.

What's inside

Ready-to-use .agent.md, .instructions.md, skills folders, hooks, agentic GitHub Actions workflows, and a cookbook with copy-paste recipes.

Install a plugin

copilot plugin install <name>@awesome-copilot — the marketplace is pre-registered in Copilot CLI and VS Code.

Learning hub

Curated guides for agents, skills, hooks, MCP servers, and the coding agent — from beginner to advanced.

Website

awesome-copilot.github.com — full-text search, filtering, plus a Tools section for MCP servers and editor integrations.

Machine-readable index

An llms.txt file provides structured listings of all resources — useful for building agents that consume the collection.

Contributing

Open to all via PR. Follow CONTRIBUTING.md for agents, instructions, and skills. The repo uses AGENTS.md for AI-guided contributions.
