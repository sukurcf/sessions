GitHub Copilot · Token optimization

Better output with less context.

A practical playbook for reducing token waste, routing work to the right model, and teaching agents your project once.

Focused workshop · May 2026

Token optimization is engineering, not prompt magic.

The best model output usually comes from smaller, sharper context: clear intent, trusted repo knowledge, compressed tool output, reusable instructions, and validation loops.

Theme: spend tokens on signal, not ceremony

I.Billing shift03

From requests to GitHub AI Credits.

Starting June 1, 2026, GitHub is moving Copilot from request-based billing to usage-based billing. Copilot usage is measured in GitHub AI Credits, where 1 AI credit equals $0.01 USD.

Base credits

Individual paid plans include monthly base credits. These match the subscription price and do not change month to month.

Flex allotment Individual only

Individual plans currently include extra monthly flex credits on top of base credits. Flex is variable and adapts as model pricing and efficiency change. Business and Enterprise plans do not include flex credits.

How they apply

Base credits are used first. If usage goes beyond base credits, flex is applied automatically at the same rates across IDE, GitHub.com, and Copilot CLI.

Team pooling and budgets

Business and Enterprise credits are pooled at the billing entity level. Budgets can track or limit additional usage by enterprise, org, cost center, or user.

Why it matters

Token hygiene becomes a cost and reliability practice. A long agent session over many files may be worth it for a production incident, but a quick question should not carry an entire repository worth of context.

Promotional amounts Jun 1 – Sep 1, 2026

Existing Business and Enterprise customers get higher included credits for the first 3 months.

II.Token accounting04

What counts as tokens?

In usage-based billing, an interaction consumes input tokens, output tokens, and cached tokens. Those tokens are priced by the model used and converted into AI credits.

Input

What is sent

Your prompt, chat history, selected code, attached files, instructions, tool schemas, retrieved context, terminal output, and tool results.

Output

What is generated

The model's answer, explanations, code edits, plans, summaries, commands, and intermediate response text.

Cached

What is reused

Context the model reuses or stores across the interaction so repeated context can be handled more efficiently.

Billed in AI credits

Copilot Chat, Copilot CLI, Copilot cloud agent, Copilot Spaces, Spark, and third-party coding agents.

Not billed in AI credits

Code completions and Next Edit Suggestions remain unlimited for paid plans according to GitHub's usage-based billing docs.

III.Billing math05

How the calculation works.

Example using GPT-5 mini rates from GitHub's usage-based pricing table: $0.25 input, $0.025 cached input, and $2.00 output per 1M tokens. 1 AI credit equals $0.01 USD.

Token typeExampleCost
Input tokens20,000 × $0.25 / 1M$0.0050
Cached tokens10,000 × $0.025 / 1M$0.00025
Output tokens3,000 × $2.00 / 1M$0.0060
Total$0.01125 / $0.011.125 credits

Formula

For each token type: tokens used × model rate per 1M tokens. Add the parts, then divide by $0.01 to convert USD into AI credits.

Optimization lesson

If the same prompt includes a huge log, open files, and repeated chat history, input tokens rise before the model writes a single line. Shrinking context directly lowers the credit draw.

Illustrative estimate only · Actual usage depends on selected model, context, caching, and product behavior.

IV.Previous billing model06

How the previous billing worked — premium requests.

Before AI credits, Copilot billed by premium requests. Each plan included a monthly allowance, and each model had a multiplier that determined how many requests were consumed per interaction.

Standard model · 1× multiplier Premium model · higher multiplier Heavy reasoning · highest multiplier
Each interaction consumed premium requests based on the model multiplier.

Plans included a fixed monthly pool (e.g., 300 for Individual, 300 per user for Business). Once exhausted, users fell back to a base model until the next billing cycle.

Requests consumed = 1 interaction × model multiplier
Remaining pool = monthly allowance − total consumed

V.Cached token flow07

How the new billing works — AI Credits .

Under the new model, every request bills by token count — not flat rate. Prior conversation turns shift into cheap cached billing, so longer sessions grow efficiently.

Cached tokens · cheap historical context Input tokens · new user message Output tokens · model response
AI credits are calculated on every request.

Each request bills input, cached, and output tokens separately at the model's rates, then converts that total cost into AI credits.

AI credits used = (input tok x input rate) + (cached tok x cached rate) + (output tok x output rate)

Request 1

Fresh prompt and response only.

Cached 0% Input 0.018% Output 0.012%
Input180 tok · u1
Output120 tok · m1

Request 2

Prior turns shift into cheap cached billing.

Cached 0.030% Input 0.009% Output 0.013%
Cached300 tok · u1 + m1
Input90 tok · u2
Output130 tok · m2

Cached share grows while fresh input stays small.

Cached 0.052% Input 0.008% Output 0.0125%
Cached520 tok · prior turns
Input80 tok · u3
Output125 tok · m3

Key takeaway: As the conversation grows, more history moves into cached billing. These examples still use only tiny fractions of a 1M-token context window.

VI.Cache mechanics · per-model TTL08

Prompt caching: pay full price once, then a fraction.

Providers reuse an exact prefix of a prompt they processed recently. A cache hit is billed far below the normal input rate and returns faster — but only an identical prefix hits, and the cache expires after an idle window called the TTL (time to live).

Model familyHow caching worksTypical TTL
OpenAI · GPT-4o → GPT-5.xAutomatic for prompts ≥ 1,024 tokens; cache hits up to ~90% cheaper5–10 min idle (max 1 hr); extended up to 24 hr on GPT-5.x & GPT-4.1
Anthropic · ClaudeAutomatic + explicit breakpoints; cache reads ≈ 10% of input rate5 min default; 1 hr optional (higher write cost)
Google · Gemini 2.5+Implicit auto-cache + optional explicit cacheImplicit automatic; explicit defaults to 1 hr, configurable

How a hit happens

Caching is prefix-based. Put stable content (instructions, context, tools) first and variable content last, so the unchanged prefix matches the next request.

What resets it

Editing anything early in the prompt, reordering files, or sitting idle past the TTL invalidates the cache, so the next request is billed as fresh input.

TTLs and discounts are provider defaults that change over time. Copilot passes through the underlying model's caching · verify current values in each provider's docs.

Instead of

Editing the system prompt or reordering attached files every turn, or starting a brand-new chat for each question.

Do this

Keep stable context as a fixed prefix, append only what is new, and continue in the same session within the cache TTL.

Prior turns bill as cache reads — as low as ~10% of the input rate — instead of full-price input on every request.
VII.Right tool for the job09

Not everything needs an agent.

On paid plans, inline Code Completions (ghost text) and Next Edit Suggestions are unlimited and are not billed in AI credits. Only agentic work — Chat, CLI, and the cloud agent — draws credits. Reach for the agent when a task genuinely needs multi-step reasoning across files.

Unlimited

Credit-free on paid plans

Completions and Next Edit Suggestions stay unlimited and do not consume AI credits, no matter how many you accept.

Use CC / NES for

Local, in-flow edits

Finishing a line, boilerplate, in-context renames, following a nearby pattern, and the repetitive edits NES can propagate for you.

Save the agent for

Reasoning across files

Cross-file refactors, planning, debugging from logs, and changes where the model must investigate and decide.

Instead of

Opening agent chat to add a null check, finish a function, or repeat the same edit down a file.

Do this

Accept the inline completion and Tab through Next Edit Suggestions for the routine edits.

Routine typing stays credit-free, so your AI-credit budget is spent only on work that actually needs an agent.
VIII.Prompt design10

Prompt for decisions, not just output.

A strong prompt gives the model the shape of success: role, target, constraints, examples, boundaries, and validation.

# High-signal prompt skeleton
Goal: fix checkout tax rounding
Scope: billing service only
Context: failing test + changed config
Constraints: no DB migration
Done when: tests pass + edge cases listed

Make success observable

Ask for code plus the exact validation path. Models produce better work when the finish line is concrete.

Give one good example

A small example of style, API shape, or expected output can replace paragraphs of abstract instruction.

Instead of

“Fix the checkout bug” with no scope — the model explores broadly, asks follow-ups, and redoes work.

Do this

Give goal, scope (billing service), the failing test, constraints (no DB migration), and a clear “done when.”

The model acts on the first pass instead of burning input and output tokens on exploration and clarifying round-trips.
IX.Persistent context11

AGENTS.md tells agents how to work here.

Copilot can use one or more AGENTS.md files in a repository. The nearest file in the directory tree can guide local behavior for monorepos, apps, packages, or special workflows.

# AGENTS.md
Always run npm test -- --runInBand before finalizing billing changes.
Generated API clients live in src/generated/; do not edit them directly.
Prefer service tests over snapshot updates for behavior changes.

What to include

Repo purpose, common commands, validation order, ownership boundaries, generated files, and safety rules.

Instead of

Re-explaining build, test, and folder rules in every new chat.

Do this

Write them once in AGENTS.md; the nearest file loads automatically.

Setup context is read once per task instead of being retyped and re-searched every session.
X.Custom instructions12

Use .instructions.md for path-specific rules.

Repository-wide instructions set the baseline. Files under .github/instructions/ can target specific paths with applyTo frontmatter.

---
applyTo: "**/*.tsx"
---

Use existing design tokens.
Prefer accessible native controls.
Add tests for user-visible states.

Best fit

Framework conventions, language style, migration rules, security standards, and review preferences that apply only to certain files.

Instead of

Pasting your style guide into every prompt so edits follow house rules.

Do this

Put path rules in .instructions.md with applyTo frontmatter.

Only the matching rule set loads for the file being edited, so you stop resending standards every turn.
XI.Reusable workflows13

.prompt.md files turn good prompts into team assets.

Prompt files are reusable workflows for tasks that happen often: reviewing a PR, preparing a release, scaffolding a component, writing tests, or summarizing migration impact.

Repeatable

Every developer invokes the same workflow instead of retyping a long prompt.

Auditable

The prompt lives in the repo, so it can be reviewed and improved like code.

Compact

Only task-specific variables need to be supplied at runtime.

Instead of

Re-typing a 30-line review or release-notes prompt every time, slightly differently.

Do this

Save it once as release-notes.prompt.md and invoke it, passing only the version or diff.

The workflow is described once and reused; only the runtime variable changes, so you stop paying to re-explain the task.
XII.Tools and automation14

Skills, hooks, and MCP reduce manual prompting.

Skills

Specialized playbooks

Package instructions, examples, and resources for domain tasks like PDF extraction, slide creation, test triage, or security review.

Hooks

Lifecycle automation

Run commands at key agent events: format after edits, block unsafe paths, or compress terminal output before it enters context.

MCP

Structured external access

Expose databases, APIs, issue trackers, search indexes, or internal tools through typed model-callable interfaces.

Real-world use case

A security team builds a review skill, attaches an MCP server for vulnerability data, and uses a hook to run secret scanning after edits — the agent gets the right workflow without a long ad hoc prompt.

Instead of

MCP tools with 300-word descriptions, long examples, and verbose payloads.

Do this

Keep each tool description to one tight sentence, use short param names, and return only the fields needed.

Tool schemas are re-sent as input tokens on every request — lean descriptions shrink that fixed per-call tax.
XIII.Tool · Graphify15

Graphify: query the map, not the whole repo.

Graphify turns code, docs, PDFs, images, SQL, and media into a queryable knowledge graph. It produces graph.html, GRAPH_REPORT.md, and graph.json, then agents can ask graph queries instead of repeatedly grepping raw files.

# Common workflow
graphify .
graphify query "what connects auth to billing?"
graphify path "UserService" "DatabasePool"
graphify hook install

Why it saves tokens

It replaces broad repo exploration with graph questions, god nodes, communities, confidence tags, and shortest paths.

Repo: github.com/safishamsi/graphify · Research note: code extraction is local via tree-sitter; docs and PDFs may use model-backed semantic extraction depending on mode.

Instead of

Asking the agent to “read the repo” to find what connects auth and billing — dozens of file reads.

Do this

Query the graph: graphify query "what connects auth to billing?"

One graph answer replaces many file reads, so far fewer tokens ever enter context.
XIV.Tool · RTK16

RTK: compact command output before it reaches the model.

RTK is a Rust CLI proxy that filters common developer commands. It uses smart filtering, grouping, truncation, and deduplication to reduce shell output by roughly 60-90% on many workflows.

rtk git status
rtk git diff
rtk test npm test
rtk err npm run build
rtk gain
rtk discover

Good targets

Git status, diffs, test runners, linting, TypeScript errors, Docker/Kubernetes output, logs, dependency lists, and cloud CLI responses.

60-90%
reduction on common command output
100+
supported command/filter categories

Repo: github.com/rtk-ai/rtk

Instead of

Piping a raw 2,000-line npm test or build log straight into chat.

Do this

Run it through rtk test / rtk err so output is grouped and deduped first.

Drops 60–90% of the tokens while keeping the failing files and error classes the agent needs.
XV.Tool · Caveman17

Caveman: reduce output tokens and memory weight.

Caveman is a skill/plugin that asks agents to respond with compressed, direct language. Its repo reports an average output reduction around 65%, with extra utilities for compressing memory files and short review comments.

Where it helps

Status updates, reviews, summaries, commit messages, memory files, and repetitive agent chatter where verbosity adds little value.

Where to be careful

Do not compress away nuance for architecture tradeoffs, stakeholder explanations, training material, or safety-sensitive decisions.

Repo: github.com/JuliusBrussee/caveman · Caveat: output compression does not reduce hidden reasoning tokens; it mainly saves visible response/context growth.

Instead of

Letting the agent emit long prose status updates and verbose memory files re-read every turn.

Do this

Switch on caveman mode for summaries, commits, and memory files.

Around 65% fewer output tokens (and smaller memory files) without losing commands, paths, or URLs.
XVI.Built-in workflow18

Use VS Code's compress output option for noisy terminals.

In VS Code 1.121, terminal tool output compression now covers more command types. Enable chat.tools.compressOutput.enabled to trim repetitive progress output before it is sent to the model.

Best inputs

Build logs, test reports, package install failures, server traces, CLI diagnostics, and long command transcripts.

What is now covered

Expanded compression includes common test runners, build tools, linters, Docker commands, and package managers, so the model sees the useful failure signal faster.

Source: VS Code 1.121 release notes · Broader compression for terminal tool output

Instead of

Sending the full 800-line build transcript that failed on one missing import.

Do this

Enable chat.tools.compressOutput.enabled so VS Code trims repetitive progress.

The model receives the failing module and stack top instead of hundreds of duplicate progress lines.
XVII.Debugging19

The Agent Debug Log panel shows what really happened in a session.

The fastest way to trace an agent run end to end: prompt-file discovery, tool calls, LLM requests, token usage, and failure points — especially for custom agents and orchestrated sub-agent workflows.

What it is

A chronological, filterable event log of what the agent did during the session, instead of only the final answer.

Why it is useful

See where tokens went, which custom instructions or tools loaded, and exactly where the path went off track.

What it contains

Logs, an Agent Flow Chart, Summary stats, Cache Explorer for prompt-cache misses, and persisted historical sessions.

How to open it

Enable github.copilot.chat.agentDebugLog.fileLogging.enabled, then run Show Agent Debug Logs.

Instead of

Guessing why a session burned so many credits and changing things at random.

Do this

Open the Agent Debug Log — Summary and Cache Explorer — to see token usage and prompt-cache misses.

You find the oversized prompt or cache-busting step and fix the real source of waste.
XVIII.Model routing20

Copilot Auto model: route by task complexity.

Auto model selection lets Copilot choose an appropriate model for the work instead of forcing every task through the same model. Use it when you want a balanced default across speed, cost, and reasoning depth.

Use Auto for

Mixed agent tasks, exploratory fixes, routine refactors, and work where the required reasoning depth is unclear.

Choose manually for

Strict latency needs, known heavy reasoning, specific model strengths, demos, or policy-controlled environments.

Token angle

The cheapest token is the one you do not need; the second cheapest is one sent to the right model for the job.

Instead of

Forcing every task through one heavyweight reasoning model by default.

Do this

Let Auto route simple edits to lighter models and reserve deep reasoning for the hard problems.

Simple tasks bill at lower token rates; you only pay premium rates when the work actually needs them.
