PART I

Copilot memories.

Two separate systems with the same name. One lives on your machine, one lives on GitHub.

II. Memory · Overview 05

Two systems, one name.

Without memory, every session starts from zero: you re-explain the same conventions, or you keep growing an instructions file by hand. Copilot solves this twice, in two different places. Both are in preview. They are complementary, not alternatives.

Local · VS Code

The memory tool

  • A built-in agent tool. Files are stored on your machine, nowhere else.
  • You or the agent write them during a chat, in plain Markdown.
  • Three scopes: your account, this workspace, this conversation.
  • On by default. You manage the lifetime yourself.

Hosted · GitHub

Copilot Memory

  • GitHub-hosted. Captured automatically while agents do real work.
  • Shared across Copilot cloud agent, code review, and Copilot CLI.
  • Stores repository facts and personal preferences, with citations.
  • Validated against the current code before it is ever used.

Rule of thumb · Local memory is for how you work in VS Code. Copilot Memory is for what the repository knows, everywhere Copilot runs.

III. Memory · VS Code 06

Three scopes on disk.

/memories/                  user scope
├── preferences.md          first 200 lines are
├── shell.md                auto-loaded every chat
│
├── repo/                   this workspace only
│   ├── build-commands.md
│   └── conventions.md
│
└── session/                this conversation
    └── plan.md             Plan agent writes here
How memories get written

Ask in plain language — "remember that we use conventional commits" — and the agent picks the scope and writes the file. The agent also records its own lessons as it works.

What survives what

User memory follows you into every workspace. Repository memory stays with this workspace. Session memory is deleted when the chat ends.

Managing the files

Command Palette: Chat: Show Memory Files to read them, Chat: Clear All Memory Files to wipe them. Deleting one file is not supported yet — ask the agent to edit it instead.

Docs · code.visualstudio.com/docs/agents/memory  ·  preview feature, stored locally

IV. Memory · GitHub 07

Copilot Memory.

As Copilot agents work in your repositories, they capture small, specific facts — and check them before reusing them.

Repository-level facts

Coding conventions, architecture decisions, build commands, project rules. Only created by contributors with write access, and only usable in that same repository.

User-level preferences

How you personally want Copilot to work with you. Created only from your own interactions, and applied only to your own sessions, across repositories.

Verified before use

Every fact is stored with citations back to the code that supports it. Copilot re-checks those citations against the current branch and drops anything that no longer holds.

Shared across surfaces

Cloud agent, code review, and Copilot CLI read the same store. Unused entries are deleted after 28 days; the clock resets each time an entry is validated and used.

Note · Code review uses repository facts only — it does not apply personal preferences

VI. Memory · Control 09

Turning it on, and cleaning it up.

# Your own preferences — view and delete github.com/settings/copilot/memory # Repository facts — review and delete Repo Settings > Copilot > Memory # VS Code local files Chat: Show Memory Files Chat: Clear All Memory Files # Copilot CLI — off by default in prompt mode copilot -p "..." --enable-memory # Copilot SDK — opt in per session memory: { enabled: true }
Individual accounts

Copilot Memory is enabled per user, not per repository — once on, it applies wherever you work. On individual plans it is on by default.

Organizations and enterprises

An administrator enables the policy first; individual users can then opt out. Admins can export or delete user-level preferences in bulk or per user.

Who can delete what

You can always view and delete your own preferences. Repository owners review and delete the repository facts. Anything unused disappears after 28 days anyway.

PART II

MCP in practice.

Connecting agents to the data and tools you already run — off the shelf, or your own.

VII. MCP · Why it became the standard 11

One protocol instead of every integration.

Before MCP, every AI client needed a bespoke integration with every tool. MCP is an open standard that defines that connection once, so a server you write is usable by every client that speaks it.

HOST

VS Code, CLI, cloud agent

Where the model and your prompt live

›

CLIENT

MCP client

Built into the host, one per server

›

SERVER

MCP server

Local process (stdio) or remote HTTP endpoint

›

SYSTEM

Your data and tools

APIs, databases, browsers, ticketing, observability

Write once, run everywhere

The same server works in VS Code, JetBrains, Xcode, Eclipse, the CLI, and the cloud agent.

The vendors already shipped

GitHub, Microsoft, Atlassian, Sentry, Cloudflare, Notion and many more publish official servers.

It replaced the alternative

Copilot Extensions built as GitHub Apps have been superseded by MCP servers.

VIII. MCP · Capabilities 12

What a server actually gives you.

Tools are the headline, but a server can offer four kinds of things.

Tools

Functions the model can call — create an issue, run a query, click a button. The agent decides when; you decide whether. Supported everywhere.

Resources

Read-only data you attach to a request: files, database tables, API responses. In VS Code: Add Context > MCP Resources.

Prompts

Prepackaged prompt templates shipped by the server, invoked in chat as /mcp.server.prompt — a way to standardise common tasks.

MCP Apps

Interactive UI rendered inline in chat — forms, visualisations, pickers — for interactions that text alone handles badly.

Important · Copilot cloud agent and Copilot code review support tools only — not resources or prompts

IX. MCP · Off the shelf 13

Start with what already exists.

Most teams need three or four servers, not twenty. These cover the common ground.

GitHub

Issues, pull requests, code search, Actions, code security. Built into Copilot CLI and on by default for the cloud agent.

Playwright

Drive a real browser: navigate, click, type, screenshot. Lets the agent verify its own UI changes instead of guessing.

Fetch & Time

Small utility servers for HTTP requests and time conversion. Both ship inside Copilot CLI already.

Sentry · Datadog

Give the agent the actual exception and the stack trace instead of your paraphrase of it.

Atlassian · Notion

Jira tickets, Confluence pages, Notion docs — the requirements the code is supposed to satisfy.

Azure · Azure DevOps · Cloudflare

Cloud resources, work items, pipelines and edge config, so infra changes are grounded in reality.

Browse · github.com/mcp — the GitHub MCP Registry, with install instructions and tool lists per server

X. MCP · GitHub server 14

The GitHub MCP server.

// .vscode/mcp.json — remote, OAuth sign-in { "servers": { "github": { "type": "http", "url": "https://api.githubcopilot.com/mcp" } } }
# Copilot CLI — already built in, but you can # widen the default tool subset copilot --add-github-mcp-toolset=actions \ --add-github-mcp-tool=search_code
What it unlocks

Read files and search code across repositories, triage issues and pull requests, inspect commits, and read Actions workflow run logs — without you pasting anything in.

Toolsets, not one big blob

Tools are grouped into toolsets — repos, issues, pull_requests, actions, code_security, web_search — selected with the X-MCP-Toolsets header on the remote server.

Read-only by default in the cloud

For the cloud agent it connects with a token scoped to read-only access on the current repository. Point it at /mcp/readonly to keep that guarantee explicit, or supply a fine-grained PAT to reach further.

XI. MCP · Playwright 15

Playwright MCP.

# Copilot CLI — one line, no file editing copilot mcp add playwright \ -- npx @playwright/mcp@latest
// .vscode/mcp.json — local stdio server { "servers": { "playwright": { "type": "stdio", "command": "npx", "args": ["-y", "@playwright/mcp@latest"] } } }
What it does

Opens a real browser and gives the agent tools to navigate, click, type, fill forms, and take screenshots — driven by the accessibility tree rather than by pixels.

Why it changes the loop

The agent can check its own front-end work: make the change, load the page, look at the result, fix what is wrong. Without it, every UI claim is unverified.

Where it is already on

Bundled in Copilot CLI, and enabled by default alongside the GitHub server for Copilot cloud agent and Copilot code review.

XII. MCP · Registries and marketplaces 16

Where the servers live.

You rarely need to hand-write configuration any more. Every surface has a browser.

GitHub MCP Registry — github.com/mcp

The curated catalogue of partner and community servers, with install instructions and tool lists. In public preview. It is the source the IDE galleries read from.

VS Code — Extensions view

Search @mcp in the Extensions view. Install adds it to your user profile; right-click > Install in Workspace writes it into .vscode/mcp.json instead.

JetBrains, Xcode, Eclipse

Open Copilot Chat, click the MCP icon, browse the registry window, and click Install next to each server you want. Xcode also accepts a custom registry URL.

Copilot CLI — /mcp search

Search the registry from inside a session, pick a server, fill in the keys, and press Ctrl+S. Experimental — run with --experimental.

Enterprise · Organizations can point every surface at a private registry URL and restrict installs to an allowlist

XIII. MCP · Configure · VS Code 17

User level, or workspace level.

// .vscode/mcp.json — commit this to share it { "inputs": [ { "id": "api-key", "type": "promptString", "password": true } ], "servers": { "context7": { "type": "http", "url": "https://mcp.context7.com/mcp", "headers": { "CONTEXT7_API_KEY": "${input:api-key}" } } } }
Workspace · .vscode/mcp.json

Checked into the repository so everyone who opens the project gets the same servers. Top-level key is servers. Use inputs for anything secret — never a literal key.

User profile · all workspaces

Run MCP: Open User Configuration. Each profile keeps its own set, and Settings Sync can carry them between machines. Use one location per server, not both.

Trust, enable, sandbox

VS Code asks you to trust a server the first time it starts. Enable and disable state is stored separately from the file, so toggling one off does not change shared config. On macOS and Linux, "sandboxEnabled": true restricts a local server's file and network access.

XIV. MCP · Configure · Copilot CLI 18

The CLI reads a different file.

# User level: ~/.copilot/mcp-config.json copilot mcp add context7 -- npx -y @upstash/context7-mcp copilot mcp add --transport http notion \ https://mcp.notion.com/mcp copilot mcp list
// Repo level: .github/mcp.json (committed) { "mcpServers": { "playwright": { "type": "local", "command": "npx", "args": ["@playwright/mcp@latest"], "tools": ["*"] } } }
Three places, clear precedence

Session flag --additional-mcp-config beats plugin servers, which beat workspace files (.mcp.json or .github/mcp.json, walking up to the Git root), which beat ~/.copilot/mcp-config.json.

.vscode/mcp.json is not read

The CLI expects the key mcpServers, not servers. Convert an existing file with jq '{mcpServers: .servers}' .vscode/mcp.json > .mcp.json.

Manage it from inside a session

/mcp show, /mcp add, /mcp edit, /mcp disable, /mcp auth. Project servers load only after you confirm folder trust, and are skipped entirely in untrusted directories.

XV. MCP · Configure · Repository & cloud 19

Repository settings, for the cloud agent.

// Settings > Copilot > MCP servers { "mcpServers": { "sentry": { "type": "local", "command": "npx", "args": ["@sentry/mcp-server@latest"], "env": { "SENTRY_HOST": "https://acme.sentry.io", "SENTRY_ACCESS_TOKEN": "$COPILOT_MCP_SENTRY_TOKEN" }, "tools": ["find_errors", "get_issue"] } } }
One config, two consumers

This block is shared by Copilot cloud agent and Copilot code review. Code review can be opted out separately with a toggle under Settings > Copilot > Code review.

tools is required — treat it as a fence

List the specific read-only tools you want. ["*"] enables everything. There is no approval prompt in the cloud: whatever you list, the agent may call on its own.

Secrets have a naming rule

Only Agents secrets and variables whose names start with COPILOT_MCP_ are visible here. Reference them as $VAR, ${VAR}, or ${VAR:-default}.

Two limits to plan around

Tools only — resources and prompts are ignored. Remote servers that require OAuth are not supported; use headers or a local server instead. Extra runtimes go in copilot-setup-steps.yml.

XVII. MCP · Build your own 21

When nothing off the shelf fits.

# pip install "mcp[cli]" from mcp.server.fastmcp import FastMCP mcp = FastMCP("deploy-status") @mcp.tool() async def get_deploy_status(service: str) -> str: """Current deploy state of a service.""" return await lookup(service) @mcp.tool() async def list_services() -> list[str]: """Every service this server knows about.""" return await catalogue() if __name__ == "__main__": mcp.run(transport="stdio")
Start from the official SDK

Servers exist for Python, TypeScript, Go, Java, C# and more. A stdio server is a normal process: the host launches it, and JSON-RPC flows over stdin and stdout.

Design for a model, not for a human

Few, well-named tools beat a thin wrapper over every endpoint. The description is the API — it is what the model reads to decide. Return structured errors it can act on.

Two rules that save you later

Write logs to stderr: stdout is reserved for protocol frames and stray text breaks the handshake. And ship read-only tools first — write tools can be added once you trust the read path.

XVIII. MCP · Security and governance 22

An MCP server runs code.

A local server is an arbitrary process on your machine with your permissions. Treat adding one like adding a dependency.

Policy at the top

The MCP servers in Copilot policy is off by default and governs Business and Enterprise seats. A second policy pins the registry URL, and an enterprise allowlist blocks anything unapproved — fail-closed if it cannot be checked.

Trust before start

VS Code prompts before starting a server for the first time; MCP: Reset Trust clears those decisions. Copilot CLI ranks sources by trust and skips repository servers in untrusted folders.

Least privilege tools

Allowlist specific read-only tools rather than ["*"]. In the CLI, --deny-tool always beats --allow-tool, so you can grant broadly and carve out the dangerous calls.

Contain what runs

Sandbox local servers on macOS and Linux with sandboxEnabled in VS Code or /sandbox in the CLI. Keep keys in inputs, env vars, or COPILOT_MCP_* secrets — never in a committed file.

Remember · Once configured for the cloud agent, MCP tools are used autonomously — the agent will not ask you first

XIX. CLI · Install and modes 24

Copilot in your terminal.

# Install (pick one) curl -fsSL https://gh.io/copilot-install | bash brew install copilot-cli winget install GitHub.Copilot npm install -g @github/copilot # Launch in the project you want to work on copilot # Start straight in plan mode copilot --plan # One-shot, scriptable, JSON out copilot -p "Summarize this week's commits" \ --allow-tool='shell(git)' \ --output-format=json
Interactive · the default

A conversation. Copilot proposes each file edit and each command; you approve once, for the session, or for this location. Shift+Tab cycles the modes.

Plan mode

/plan explores and asks clarifying questions but is blocked from editing your project files — the restriction is enforced, not merely requested. Approve the plan to leave the mode.

Autopilot

Copilot keeps working until the task reports complete, then hands control back. Cap it with --max-autopilot-continues.

Programmatic · -p

Runs one prompt and exits — the CI and cron shape. Pair with an approval flag, because there is nobody there to answer a prompt.

Twenty-eight commands worth memorising.

Session & context

Models & agents

/model — switch model, reasoning effort, context tier /agent — choose a built-in or custom agent /rubber-duck — second opinion from a different model /subagents — set default models for subagents /tasks — watch running subagents and shells

Setup & extensibility

XXII. CLI · Giving it context 27

Feeding the context window.

Everything competes for the same window: system prompt, tool schemas, your files, and every command's output. These are the controls.

Pull things in

@ path/to/file inlines a file. # 1234 pulls in a GitHub issue or pull request. --attachment attaches a file or image to the opening prompt. ! command runs a shell command and keeps the output.

Set the working set

The CLI is scoped to the directory you launched it from. /add-dir widens that, /list-dirs shows what is allowed, /cwd moves it. Never launch it from your home directory.

Watch the window

/context breaks usage down by system prompt, instructions, tools, MCP tools, and messages. Compaction starts automatically at about 80% and each compaction leaves a numbered checkpoint you can read back.

Standing instructions

Instruction files are merged, not ranked — all of the files below load together. copilot init writes the first one for you by reading the codebase.

XXIII. SDK · What it is 28

XXV. SDK · Python 30

One file, one working agent.

import asyncio from pydantic import BaseModel, Field from copilot import CopilotClient, define_tool from copilot.session import PermissionHandler from copilot.session_events import AssistantMessageData, SessionIdleData class LookupIssueParams(BaseModel): id: str = Field(description="Issue identifier") @define_tool(description="Fetch an issue from our tracker") async def lookup_issue(params: LookupIssueParams) -> str: return await fetch_issue(params.id) async def main(): async with CopilotClient() as client: async with await client.create_session( model="gpt-5", on_permission_request=PermissionHandler.approve_all, tools=[lookup_issue], ) as session: done = asyncio.Event() def on_event(event): match event.data: case AssistantMessageData() as d: print(d.content) case SessionIdleData(): done.set() session.on(on_event) await session.send("Fix the bug in issue AB-42") await done.wait() asyncio.run(main())
A session is the unit of work

One client can run many independent sessions, each with its own model. Both are async context managers, so the runtime process is torn down for you. Sessions persist to disk, so resume_session() picks a conversation back up later.

Your tools sit next to the built-ins

@define_tool turns a Pydantic model and an async function into something the model can call. Your process runs the handler and the result flows straight back into the conversation.

Permissions are yours to decide

approve_all is the demo path. In production, pattern-match each request — shell, write, read, mcp, custom-tool, url, memory or hook — and return PermissionDecisionApproveOnce() or PermissionDecisionReject(feedback=…), which the model reads and adapts to.

Events, not polling

Subscribe once and match on the event data: AssistantMessageData, AssistantMessageDeltaData for streaming, tool execution events, and SessionIdleData to know when a turn is finished.

XXVI. SDK · Python in production 31

Past the demo path.

from copilot.rpc import ( PermissionDecisionApproveOnce, PermissionDecisionReject) from copilot.session_events import PermissionRequestShell def on_permission_request(request, invocation): match request: case PermissionRequestShell(full_command_text=cmd): return PermissionDecisionReject( feedback=f"Shell denied: {cmd}") case _: return PermissionDecisionApproveOnce() async def on_pre_tool_use(data, invocation): return { "permissionDecision": "allow", "modifiedArgs": data.get("toolArgs"), "additionalContext": "Target staging, never prod", } async with await client.create_session( model="gpt-5", streaming=True, on_permission_request=on_permission_request, hooks={"on_pre_tool_use": on_pre_tool_use}, memory={"enabled": True}, infinite_sessions={ "background_compaction_threshold": 0.80}, ) as session: await session.send("Roll out the config change")
Decide, do not rubber-stamp

The request is a discriminated union — match on the variant to read its fields. Return PermissionDecisionApproveOnce(), a reject with feedback the model reads, or a longer-lived ApproveForSession / ApproveForLocation / ApprovePermanently.

Hooks wrap every tool call

on_pre_tool_use can allow, deny, or rewrite the arguments before the tool runs. on_post_tool_use and on_post_tool_use_failure feed context back afterwards; prompt, session start and end, and error hooks complete the set.

Built for long-running work

Infinite sessions compact context in the background at a threshold you choose, so a session does not die when the window fills. memory is opt-in per session.

Fetch the runtime once

python -m copilot download-runtime caches the Copilot binary ahead of time — worth doing in a container image rather than on first request.

XXVII. SDK · What you get 32

The control surface.

Everything below is configuration on a session — not something you build.

Custom tools

Expose your own functions with typed schemas. Override a built-in tool deliberately with overridesBuiltInTool, or skip its prompt with skipPermission.

Permission control

Approve once, for the session, for the location, or permanently. Reject with feedback the model reads and adapts to.

Session hooks

onPreToolUse can rewrite arguments or block a call. onPostToolUse, failure hooks, prompt hooks, start and end hooks round it out.

Slash commands & dialogs

Register /deploy-style commands that call your code, and ask the user structured questions through elicitation when the host supports it.

Long sessions, kept honest

Infinite sessions compact context in the background at configurable thresholds; opt in to memory; export OpenTelemetry traces for every session, message and tool call.

Bring your own model

Point a session at any OpenAI-compatible endpoint, Azure OpenAI, or Anthropic — including a local Ollama — with provider. Key-based auth only.

Prompt shaping · systemMessage appends by default; customize edits named sections; replace drops every guardrail — use it knowingly
