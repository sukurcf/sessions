Agent mode is not the cloud agent

Agent mode edits your local working tree and stops when you close the editor. The cloud agent runs remotely on Actions runners and produces a branch and a pull request.

I. Foundations · How it works 06

Prompt, context, completion.

GitHub documents the process as four stages, and every feature is a variation on this loop. The one sentence that explains most confusion: a large language model is a document completion engine, and GitHub Copilot's job is to build a document whose most likely continuation is the code you wanted.

STAGE 1
Input processing

Surrounding code is pre-processed and combined with context such as open tabs, then sent to the model as a single prompt.

→
STAGE 2
Model analysis

The large language model processes the assembled prompt. It sees nothing that was not put in the prompt.

→
STAGE 3
Response generation

The model generates a continuation. Several candidates may be produced for a single request.

→
STAGE 4
Output formatting

The result is shown inline, visually distinct, and applied only when you explicitly accept it.

Everything the model will ever know about this request arrives in stage 1

Four kinds of token are billed

Input, output, cached input, and reasoning. Cached input is roughly one tenth the price of fresh input, which is why a stable conversation prefix is cheaper than a rewritten one.

Tokenization is not intuitive

The same word with different capitalisation or leading whitespace becomes a different token. Consecutive spaces each consume a token. Tables are more compact than JSON because JSON repeats every field name on every row.

I. Foundations · Non-determinism and model choice 07

Different answers, different models.

Variation is documented behaviour, not a defect. GitHub states plainly that "due to the non-deterministic nature of AI, Copilot may not always follow your custom instructions in exactly the same way every time they are used."

Six reasons the same prompt gives a different answer

Sampling. Generation is probabilistic, and temperature and top-p are not published — treat exact reproducibility as unavailable rather than tunable.
Which tabs were open. The 20-tab cap means the prompt differs when your editor state differs.
Which snippets survived truncation. Around 95% of requests drop context, chosen by similarity to the cursor position.
Conversation history. Compaction may have summarised earlier turns differently between sessions.
Automatic model selection. Auto mode may route the same prompt to a different model on a different day.
Models are retired underneath you. Eight deprecations were announced between February and July 2026.

Practical rule. Do not build a process that depends on GitHub Copilot producing identical output twice. Build processes that verify output instead: tests, type checks, linters, code review. That is what modules 5 through 7 are about.

The model selection rule

Use a small fast model for mechanical work: renames, boilerplate, straightforward tests, quick questions. Use a reasoning model where being wrong is expensive: architecture, subtle bugs, security review, large refactors. Automatic selection applies a 10% discount on model costs and is a reasonable default.

Concatenated into one prompt · only layer 7 has no natural upper bound

The sentence to write on a whiteboard: "This assembled prompt is what the model sees. Everything outside of it is invisible to the model." Almost every "Copilot ignored my requirement" complaint is a context assembly problem, not a model quality problem.

Layer 7 is the one that surprises people

When an agent runs a text search or grep, every match returned becomes part of the context, even if the agent never opens the file. Generated files, build output, logs, and datasets can fill the window with noise.

Three ways to keep noise out

.gitignore excludes from text search, grep, and the semantic index. files.exclude also removes from Explorer. search.exclude removes from search and grep but keeps files in Explorer.

Two things that are easy to forget

Reasoning tokens consume the budget even though they are never shown. And there is no memory between sessions — anything the model needs must be re-supplied, which is what instruction files and memory files are for.

I. Foundations · Practice 10

Ten habits that fix most bad answers.

  • Start a new session for a new task. Old history is not free; it is tokens and it is noise.
  • Be selective. Attaching the entire codebase is not helpful and often makes results worse.
  • Keep planning, coding, testing, and debugging in separate sessions.
  • Compact with guidance rather than letting automatic compaction choose what to discard.
  • Fork instead of re-prompting when you want to try a different direction from a known good point.
  • Delegate investigation to a subagent so its findings do not fill your main window.
  • Turn off tools you are not using. Every enabled tool costs description tokens and widens the decision space.
  • Exclude generated files, build output, and logs from search.
  • Use code terms. Function names, class names, and concepts that actually appear in the code.
  • Avoid vague pronouns. "What does this do" is ambiguous between the last answer, the current file, and the whole project.

Diagnostic: used references

Expand the "Used N references" dropdown on any response to see exactly which files and instruction files fed it.

Diagnostic: customizations

Right-click the Chat view → Diagnostics. Lists every loaded instruction file, agent, and skill, plus load errors.

Diagnostic: cache

The Cache Explorer shows your prompt cache hit rate. A stable prefix means cheaper and faster requests.

II. In-editor · Next edit suggestions 13

Two systems, one Tab key.

"Based on the edits you're making, next edit suggestions predict both the location of the next edit you'll want to make and what that edit should be." The reasoning, from the VS Code team: most coding activity is editing existing code, not writing new code, and edits are rarely made in isolation.

How one Tab key does two jobs. VS Code resolves it with two mutually exclusive context keys. When a suggestion is elsewhere in the file, Tab jumps to it; when you are at the suggestion, Tab accepts it. Tab to navigate, Tab again to accept. Esc rejects, ⇧ Tab applies as a symbol rename, ⌥ \ triggers manually.

The gutter arrow

Points up or down toward the suggestion's location. Hovering opens Go To, Accept, Reject, Show Collapsed, Settings, and Feedback. Once you accept, you can keep accepting with single Tab presses until you start typing again.

What it catches

Mistakes. Typos such as cont x = 5, inverted ternaries, conditions that always evaluate true such as a !== 'x' || a !== 'y'.
Follow-through on intent. Rename Point to Point3D and it proposes adding a z field, then updating the distance calculation.
Refactoring. Rename a variable once and it proposes the same change everywhere else.
Style after a paste. Adjusts pasted code to the conventions of the surrounding file.
Cross-file work. Add a command in extension.ts, open package.json, and it proposes registering it.
Diagnostics. With nextEditSuggestions.fixes enabled, it is driven by compiler and linter squiggles.

// Prompt: "add error handling to the payment service" 1. semantic search ─▶ find payment-related code 2. grep ─▶ find existing error patterns 3. usages ─▶ trace all call sites 4. file search ─▶ locate config and tests 5. read files ─▶ make coordinated changes 6. run tests ─▶ validate 7. read failures ─▶ iterate from step 3

What it can do that Ask cannot

Multi-file edits — plans the approach, edits across the project, runs commands, corrects itself. Parallel sessions — several at once, each with its own context window. Handoff — move an in-progress session to GitHub Copilot CLI or the cloud agent with full history.

Request cap. chat.agent.maxRequests defaults to 25. When an agent stops mid-task, this is often why. Raise it deliberately rather than by reflex — a runaway loop costs credits.
Prerequisite and cost. Agent mode requires chat.agent.enabled, and organizations can disable it through the ChatAgentMode policy. Since billing moved to tokens, every tool call costs you too, because each tool result is fed back as input tokens. Long agentic sessions are the main cost driver.
III. Chat modes · Permissions and terminal safety 18

Four permission levels.

This is the single most important control to understand before letting an agent run. Set the default with chat.permissions.default; it can be changed mid-session.

LOWER RISK
HIGHER RISK
LEVEL 1
Default Approvals

Uses your configured approval settings. Tools that need approval show a confirmation dialog. When uncertain, the agent asks clarifying questions.

LEVEL 2 · EXPERIMENTAL
Assisted permissions

A language model judge evaluates the risk of each tool call. Approved calls run automatically; the rest show a dialog. Enable with chat.assistedPermissions.enabled.

LEVEL 3
Bypass Approvals

Auto-approves every tool call. The agent still asks clarifying questions.

LEVEL 4
Autopilot

Auto-approves every tool call and auto-answers clarifying questions, so the agent never stalls. Continues until it decides the task is complete.

// Terminal approval is evaluated per command, // because one tool can run anything. "chat.tools.terminal.autoApprove": { "mkdir": true, "/^git (status|show\\b.*)$/": true, "del": false, "/dangerous/": false } // Every subcommand must match a true entry // and must not match a false entry. "chat.tools.edits.autoApprove": { "**/.env": false }
The warning, quoted. "Bypass Approvals and Autopilot bypass manual approval prompts, including for potentially destructive actions like file edits, terminal commands, and external tool calls." The confirmation dialog shows the tool name and its input parameters, you can edit those parameters before allowing, and you choose the scope: single use, this session, this workspace, or all future invocations.
The documented weaknesses — teach these honestly. Sub-command extraction uses PowerShell and bash tree-sitter grammars, so there is no zsh or fish grammar and unrecognised patterns are not detected. Detection of file writes is minimal. The docs give a concrete bypass: find -exec is blocked, but find -e"x"ec is not.
The conclusion the docs draw. "If prompt injection is a possibility or you're in a high-risk environment, consider enabling agent sandboxing or running VS Code within a container." Auto-approval rules alone are not a security boundary.

Redo restores changes you rewound by mistake. Fork from a checkpoint branches into a new session containing history only up to that point, so you can try a different approach without losing the original.

III. Chat modes · Sessions, subagents, memory 20

Sessions, subagents, memory.

Sessions

Four dials per session

Agent type local, CLI in the background, cloud, or third-party. Agent Agent, Plan, Ask, or a custom agent. Language model any model available to you. Permission level the four levels opposite.

The sessions list

Name, workspace, agent type, status, and added and removed line counts. Filter by state, group by workspace or timeframe, pin what matters. The Chat view and the Agents window share the same sessions.

Archive, delete, export

Archiving does not delete: a Git worktree is removed only when the working tree is clean, and the branch and commits are preserved. Delete is permanent. Chat: Export Chat... writes JSON.

Subagents

# Automatic delegation Suggest ways to refactor this legacy code. # Direct invocation by name Use the testing subagent to write unit tests for the authentication module. # Explicit tool call Evaluate the #file:databaseSchema using #runSubagent and generate an optimized data-migration plan.

Its purpose is context, not capability

A subagent runs in its own context window, does not inherit conversation history, receives only the task prompt, and returns only a summary. The main agent waits, but VS Code can spawn several at once.

Limits

They cannot nest unless chat.subagents.allowInvocationsFromSubagents is enabled, and even then the maximum depth is five. A subagent cannot exceed the cost tier of the main model — it falls back instead.

Three kinds of tool.

Context. Fewer tool calls means less context consumed by intermediate results.
Cost. Every tool call produces output that becomes billable input tokens.
Relevance. A smaller decision space produces better tool choices.
Speed. Fewer active tools means faster responses.

VI. Extending · Transports and trust 39

Transports and security principles.

Two standard transports

stdio — newline-delimited JSON-RPC over the standard streams of a subprocess the client launches. Use for anything running on the same machine.
Streamable HTTP — each message is an HTTP POST to a single endpoint; replies arrive as a JSON object or a request-scoped event stream. Use for remote and shared servers.

Standalone HTTP+SSE is legacy. VS Code and GitHub Copilot CLI still accept sse for backward compatibility, but do not build new servers on it.

Authentication. The specification separates the MCP server (a resource server) from the authorization server, so you delegate to an existing identity provider. VS Code has built-in support for GitHub and Microsoft Entra, tries dynamic client registration first, and falls back to client credentials.

Four security principles from the specification

User consent and control — explicit consent for all data access and operations.
Data privacy — hosts must not transmit resource data elsewhere without consent.
Tool safety — "Tools represent arbitrary code execution… descriptions of tool behavior such as annotations should be considered untrusted, unless obtained from a trusted server."
Sampling controls — users approve sampling requests and control what the server can see.

Read the third principle twice. A tool description is data supplied by a third party that goes directly into your model's context. That is a prompt injection surface. Review a server before you trust it.

A minimal server, and how to test it.

The number one bug, on every SDK: for stdio servers, never write to stdout — it corrupts the JSON-RPC framing and breaks the server silently. TypeScript: console.error, never console.log. Python: the logging module, never print. Go: log.Println, never fmt.Println. This does not apply to HTTP servers.

VII. Advanced · Orchestration and multi-agent patterns 45

Running several agents at once.

<!-- Coordinator and workers --> --- name: Feature Builder tools: ['agent', 'edit', 'search', 'read'] agents: ['Planner', 'Plan Architect', 'Implementer', 'Reviewer'] --- For each feature request: 1. Use Planner to break the feature into tasks. 2. Use Plan Architect to validate the plan against existing codebase patterns. 3. Two surfaces, one session store

The Chat view is code-first and scoped to the open workspace; the Agents window is agent-first and works across all workspaces. Previous sessions keep running in the background — the list shows status, agent type, and line counts.

Cross-session tools and forking

Agent-host sessions can list sessions, create a session for a sub-task, read another session's recent context, and send it a message — always with your confirmation. /fork branches the whole session and inherits history, which preserves the prompt cache and reduces cost.

Multi-perspective review

Run four subagents in parallel so their findings are independent and unbiased: a correctness reviewer for logic and edge cases, a code quality reviewer for readability and duplication, a security reviewer for input validation and injection, and an architecture reviewer for pattern consistency. Then synthesise a prioritised summary.

Recursive divide and conquer

An agent that lists itself in its own agents field. If the input has more than four items, split it in half and delegate each half to a copy of itself; otherwise process directly, then merge results. Requires chat.subagents.allowInvocationsFromSubagents, with a maximum depth of five.

Concurrency by plan, and the CLI's built-in agents

Free and Education 2 · Pro and Pro+ 4 · Max 8 · Business 16 · Enterprise 32; only usage-based billing accounts can raise these with subagents.maxConcurrency. Built-in CLI agents: explore, task, general-purpose, code-review, security-review, research, and rubber-duck.

The failure mode to avoid. VS Code names it directly: "Over-engineering agent chains — deeply nested subagent workflows and excessive tool calls multiply token usage." Two levels solves most problems. Five levels mostly generates a bill.

The prompt technique that makes scripting work

Constrain the output format in the prompt itself. "Give the number only. No other text." and "Reply only YES or NO." are doing the real work — without them you get a paragraph your script cannot parse.

Do not depend on process exit codes. GitHub documents hook exit codes exhaustively but does not publish an exit-code table for the copilot process in prompt mode. Parse the output, or use --output-format=json, rather than branching on exit status.
GitHub's own recommendation comes first. "For most automation use cases, we recommend using GitHub Agentic Workflows rather than invoking copilot directly in workflow steps. Agentic workflows use GITHUB_TOKEN authentication by default and include additional guardrails suited for automated environments." The project is github/gh-aw.

Authentication, and no first-party action

GITHUB_TOKEN is recommended for organization-owned repositories and needs no secret. Otherwise use a fine-grained personal access token with the GitHub Copilot Requests permission, exposed as COPILOT_GITHUB_TOKEN. No copilot GitHub Action is documented — the two supported paths are agentic workflows, or npm install plus a run: step.
