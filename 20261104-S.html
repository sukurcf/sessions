Review process

Copilot finds possible issues and suggests changes. A developer checks the findings.

Use local review for early feedback. Use pull request review for shared feedback and repository context.

VS Code

Review code before you push. You can review a selection or uncommitted changes.

  1. Select

    Select code. Open the context menu and choose Review.

  2. Review changes

    In Source Control, use Copilot Code Review - Uncommitted Changes for your working changes.

  3. Apply

    Read inline comments and the Comments or Problems view. Apply or discard each suggestion.

Applied edits are not committed automatically. Inspect the diff and run the relevant tests before you commit.

Pull request review

On GitHub.com, open a pull request. Under Reviewers, select the effort level and request Copilot.

GitHub.com

  1. Find Copilot under Reviewers.
  2. Select Request.
  3. Read the overview and inline comments.
  4. After changes, select Re-request review, unless new pushes trigger it.

REST API

Request the code review bot, not the cloud agent.

POST /repos/OWNER/REPO/pulls/NUMBER/requested_reviewers

{
  "reviewers": [
    "copilot-pull-request-reviewer[bot]"
  ]
}

Review time varies. Do not promise a fixed completion time for a live demonstration.

Review comments

Use severity to decide what to inspect first. Severity does not prove that the finding is correct.

Read the result

  • Read the overview, effort label, and finding status.
  • Inspect High, Medium, and Low comments.
  • Check grouped suggestions against the actual code.

Record the decision

  • Confirm the issue and check the proposed change.
  • Use a resolution reason: Addressed, Won't fix, or Incorrect.
  • Replies are not a chat with Copilot. A reply to leave an issue open can prevent auto-resolution.

A normal review is a Comment review. An approval assessment in the overview is not, by itself, an approving review.

Settings map

Separate access, review triggers, effort, context, and merge authority. They are different controls.

Separate pages: automatic review rulesets, access policies, paid usage, budgets, Runner type, Internet access, MCP servers, and Memory.

Enterprise settings

AI controls → Available Agents → Copilot code review sets enterprise-wide controls.

Copilot code review
Select the access policy. Then select the code review features allowed in the enterprise.
Default review effort level
Set the default. Organizations and repositories can override this default.
Maximum review effort
No limit / Lite / Balanced / Max. Organizations and repositories cannot exceed this limit.
Paid-member billing
Member / Organization / Let organizations decide. Organization billing requires AI credits paid usage.
Allow Copilot to approve pull requests
Let organizations decide / Enable for selected organizations / Disabled everywhere. Disabled everywhere is the default.

For enterprise automatic reviews, create an enterprise branch ruleset and target the required organizations, repositories, and branches.

Organization settings

Settings → Copilot → Code review. Enterprise restrictions still apply.

Default review effort level
Choose Lite, Balanced, or Max for automatic reviews. Repositories can override the default.
Maximum review effort
No limit / Lite / Balanced / Max. Each repository can use this level or a lower level.
Choose how members with a Copilot license are billed
Member uses the member's entitlement by default. Organization bills the organization.
Count Copilot approvals toward merge requirements
Enabled everywhere / Let repositories decide / Enable for selected repositories / Disabled everywhere.
Only allow Copilot code review to be triggered by authorized users
Restrict review requests that use external Copilot licenses. Repositories cannot turn off this organization restriction.

Repository settings

Settings → Copilot → Code review. Repository administrators configure these controls within policy limits.

Review effort level
Set the effort for automatic reviews: Lite, Balanced, or Max.
Maximum review effort
No limit / Lite / Balanced / Max. A local limit cannot relax an organization or enterprise limit.
Auto-approval
Set Allow Copilot to approve pull requests and, separately, Allow Copilot approvals to count toward merge requirements.
File paths
Limit which approvals count. Use up to 15 globs, one per line. Every changed file must match an allowed glob.
Authorized users
Enable the authorized-user restriction locally, or inherit it when the organization requires it.

Automatic reviews use rulesets, not the effort control. The authorized-user restriction blocks unauthorized personal triggers, but ruleset reviews still run.

Automatic reviews

A personal setting and an applicable ruleset are independent sources. Either can start a review.

Review new pushes: review each push. Review draft pull requests: review early drafts. Each option applies if either source enables it.

Personal automatic review needs an eligible paid plan and is unavailable for managed user accounts. Organization and enterprise rulesets also select their target repositories or organizations.

Review effort

Choose the depth of review, not a model. Copilot manages its review models.

Select effort under Reviewers before a request, or set a default. Check the overview to see the effort used for each run.

Effort selection and limits

Copilot uses the first applicable effort choice. A maximum is a limit, not a default.

  1. Effort selected for this request
  2. Effort previously used on this pull request
  3. Requestor's personal effort preference
  4. Repository default
  5. Organization or owner preference
  6. Built-in fallback: Balanced
Enterprise maximum: Balanced
Organization and repository: Lite or Balanced only.Max blocked

Enterprise defaults can be overridden, but limits cannot. For a new PR, the requestor is the author. Manual reviews also use effort. Turning off automatic review does not clear a personal effort preference.

Approvals

Three separate controls determine whether a Copilot review can satisfy a merge requirement.

New commit: the Copilot approval is dismissed. Request another review. Human review and required checks remain important.

Approvals are off by default. Configure path restrictions separately when approvals must count only for selected files.

Approval paths

Every changed file must match an allowed path. One unmatched file prevents the approval from counting.

Example allowed paths: docs/** and *.md

Documentation only

docs/setup.mdMatch
README.mdMatch

All files match: the approval can count.

Mixed changes

docs/setup.mdMatch
src/pay.tsNo match

One file fails: the approval cannot count.

Use up to 15 globs, one per line. Leave the list blank to allow counting approvals for all file paths.

Access and billing

Access policy and billing source are separate. Changing the payer does not grant review access.

Licensed members
Choose Member or Organization billing. Enterprise policy can let organizations decide. Organization billing needs paid AI-credit usage.
Members without a license
Enable AI credits paid usage, then Allow members without a Copilot license to use Copilot code review in GitHub.com (off by default). Enterprise-set policy locks organization control. Not IDE access.
Automatic and manual
Automatic usage normally goes to the PR author. A manual request normally goes to the requestor, subject to billing policy.
Bots and cloud agent
Other bot usage is billed to the organization. Cloud-agent PRs first use the human co-author's billing, then the organization if needed.
Budgets
AI credits and Actions compute are separate cost components. Applicable budget or spending limits can block review. A budget is optional for organization billing.

Instructions and skills

Use clear, testable rules. Copilot reads review instructions and skills from the PR's head branch.

Choose the right file

  • .github/copilot-instructions.md: repository-wide Copilot rules.
  • .github/instructions/*.instructions.md: path-specific rules with applyTo.
  • AGENTS.md: shared rules for agents.
  • .github/skills/code-review/SKILL.md: a review workflow used when relevant.

Path-specific example

---
applyTo: "src/api/**/*.ts"
---
Check authorization on new routes.
Check error handling for service calls.
Check tests for rejected requests.
Do not flag intentional retry patterns.

Keep the user's Use custom instructions preference enabled when these rules should apply.

The current guide also lists CLAUDE.md, GEMINI.md, and REVIEW.md as review instruction sources.

Memory

Code review uses repository facts, not user-level preferences. Their controls are separate.

Organization repository access
Choose All repositories (default), Selected repositories, or No repositories, subject to enterprise restrictions.
Repository switch
Settings → Copilot → Memory → Allow Copilot to store and retrieve repository facts. Turn off to stop creation and use; existing facts are not deleted.
Retention
Enterprise and organization owners can set repository-fact retention to 7–180 days. The shorter policy applies. Default: 90 days since creation or last upvote.
Personal-memory policy
The enterprise and organization Copilot Memory policy controls user preferences. Turning it off alone does not disable repository facts.

Use instruction files for rules that must be provided consistently. Check and remove incorrect stored facts from repository Memory settings.

MCP settings

MCP provides external evidence. Open Settings → Copilot → MCP servers.

Allow Copilot to use MCP tools when reviewing pull requests is on by default. Turn it off to leave repository MCP available to cloud agent but not code review.

MCP JSON is shared with cloud agent. GitHub and Playwright servers are on by default. Use COPILOT_MCP_* Agents secrets or variables. Tools only; no prompts, resources, remote OAuth, or per-call approval prompt. Check View session for setup and tool calls.

SonarQube

Use code quality and security evidence. Run CI analysis for the current PR commit first.

Setup

  1. Run SonarQube Server or Cloud analysis.
  2. Deploy the official MCP server with SONARQUBE_READ_ONLY=true.
  3. Allowlist required tools marked readOnlyHint: true.
  4. Provide the project key and analyzed PR or branch.

HTTP configuration shape

{"mcpServers": {
  "sonarqube": {
    "type": "http",
    "url": "$COPILOT_MCP_SONAR_URL",
    "headers": {"Authorization":
      "$COPILOT_MCP_SONAR_AUTH"},
    "tools": ["<read-only-tool>"]
  }
}}

Template only. Use your MCP endpoint and auth header. Tool availability depends on version, toolsets, permissions, and entitlements. Official tool catalog.

SonarQube findings

Use these official read tools to check whether a reported issue is relevant to the PR.

Find the analyzed PR
search_my_sonarqube_projects and list_pull_requests: find the project and analysis PR key. Use list_branches for branch analysis.
Read issues
search_sonar_issues_in_projects: filter by project, PR or branch, severity, and issue status. Compare the returned file and line with the diff.
Explain the rule
show_rule: retrieve the rule explanation. Check why the pattern is unsafe before accepting a proposed fix.
Inspect security hotspots
search_security_hotspots and show_security_hotspot: retrieve code context, flows, and rule details. A hotspot needs review; it is not proof of a vulnerability.

Keep write tools out of the review allowlist. Examples: change_sonar_issue_status and change_security_hotspot_status. A review must not silently accept or close findings.

SonarQube quality

Use measured results to focus review effort. MCP retrieves evidence; it does not replace CI checks.

Quality gate
get_project_quality_gate_status: inspect the analyzed PR's gate result. get_component_measures: read coverage, complexity, or other selected metrics.
Test coverage
search_files_by_coverage and get_file_coverage_details: identify uncovered lines and partially covered branches. Compare them with changed error and authorization paths.
Dependency risks
search_dependency_risks: inspect SCA findings linked to the analyzed project. Requires Advanced Security; Server requires 2025.4 Enterprise or later.
Duplicated code
search_duplicated_files and get_duplications: locate repeated code and compare a changed implementation with its related copies.

Select the PR or branch where the tool supports it. Check analysis freshness. A passing gate does not prove that the PR has no defects.

SonarQube review

Put the review task in the PR description and reusable rules in head-branch review instructions.

  1. Provide scope

    Give the SonarQube project key, analyzed PR key, current commit, and files to inspect. Wait for CI analysis.

  2. Request review

    Request Copilot under Reviewers. The agent can select relevant, available read-only MCP tools.

  3. Check evidence

    Open View session. Confirm tool calls and analysis scope. Inspect each finding, fix the code, rerun CI, and request review again.

Example review task: “Use SonarQube project payments-api, analysis PR 42. Compare open issues and uncovered branches with this diff. Explain relevant rules. Report only supported findings with file, line, and issue ID. Do not change issue status.”

Example identifiers only. Instructions guide tool selection; they do not guarantee a call. IDE-bridge analysis tools need a running IDE and are not assumed available in a GitHub-hosted review.

Wiz

The official Wiz MCP exposes cloud security context. Use its read capabilities to assess the production risk behind a change.

Issues and findings
Retrieve security issues, vulnerabilities, and affected resources. Compare a linked finding or CVE with a dependency, container, or code change.
Inventory and exposure
Query cloud resources and configurations. Check whether a Terraform change relates to an internet-facing resource or sensitive data.
Security Graph
Read relationships, attack paths, identities, and ownership. Assess whether exposure and permissions combine into a higher-risk path.
Agent analysis
Where available, retrieve Wiz agent analysis and remediation guidance, including Green Agent recommendations. Compare the proposed fix with the affected code.

These are verified capability groups, not exact tool identifiers. Confirm your tenant's tool schemas, permissions, entitlements, and readOnlyHint annotations. Official Wiz MCP overview.

Wiz MCP configuration

{
  "mcpServers": {"wiz": {
    "type": "http",
    "url": "$COPILOT_MCP_WIZ_URL",
    "headers": {"Authorization": "$COPILOT_MCP_WIZ_AUTHORIZATION"},
    "tools": ["<verified-read-only-tool>"]
  }}
}

Example shape only. Replace the URL, auth header, and tool name with values from your Wiz tenant. Put credentials in COPILOT_MCP_* secrets. Remote OAuth is unsupported. Every enabled tool must have readOnlyHint: true; calls run without approval. See the Wiz setup guide.

Runners

Actions runners provide project context and tool use. The organization runner default is shared with cloud agent.

Organization default
Settings → Copilot → Runner type. Choose Standard GitHub runner or Labeled runner.
Repository override
Allow repositories to customize the runner type controls whether repository workflow files can override the organization default.
Repository workflow
Use .github/workflows/copilot-code-review.yml. Without it, review uses copilot-setup-steps.yml. Set jobs.copilot-setup-steps.runs-on.
Runner choices
Standard GitHub-hosted is the default. Larger runners cost more per minute. Self-hosted review supports only ARC-managed Ubuntu x64 Linux runners.
Network and fallback
Restrict network access and allow required GitHub hosts. If runner capabilities are unavailable or fail, review can continue with fewer features.

Internet access

Open Settings → Copilot → Internet access at organization or repository level. Use the Copilot code review section, not the cloud-agent section.

Enable firewall
Organization: Enabled / Disabled / Let repositories decide. A repository can change its switch only when policy lets it decide.
Recommended allowlist
The same three organization choices apply. The recommended list allows common dependency and browser-download hosts.
Allow repository custom rules
Organization: Enabled by default, or Disabled. This controls whether repositories can add allowlist entries.
Custom allowlists
Organization and repository entries are combined. Repositories cannot remove organization entries. Add a domain or a URL scoped to a path.

The firewall does not directly cover MCP server processes or setup steps. Use runner network controls as well.

Review limits

A review is useful feedback, not proof that the change is correct or secure.

Files and context

  • Dependency management files, logs, and SVG files are excluded.
  • Generated, vendored, and bundled paths can also be excluded.
  • Check applicable content-exclusion policy before a demonstration.

Analysis and policy

  • Copilot can miss issues or report an incorrect finding.
  • Review model selection is not supported. Chat model policy does not select review models.
  • Use tests, required checks, and human review with Copilot feedback.

Use a small source-code change with a known issue for a demo. Do not use a lock file or generated file as the only example.

Fixes with cloud agent

Use a code suggestion for a small edit. Use cloud agent for a task that needs coordinated changes.

  1. Collect

    Group related findings. Record the affected code, expected behavior, and relevant tests.

  2. Delegate

    Select Fix with Copilot on a Copilot comment. Edit the draft request to include the related findings.

  3. Check

    Choose a commit to the same PR or a new PR against its branch. Inspect the changes, run checks, and request review again.

Both code review and cloud agent must be enabled. For simple compatible suggestions, you can also apply a group in one commit.

The handoff to cloud agent is in public preview. Do not include unrelated changes in the fix request.

CI checks

Use repeatable tools for lint and spelling checks. Use Copilot to explain issues that need code context.

name: Content checks
on: [pull_request]
permissions: { contents: read }
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: DavidAnson/markdownlint-cli2-action@v24
        with: { globs: '**/*.md' }
      - uses: codespell-project/actions-codespell@v2

Merge policy

  • Save the workflow in .github/workflows/.
  • Set Markdownlint rules in .markdownlint-cli2.jsonc.
  • Set Codespell rules in .codespellrc or pyproject.toml.
  • Require the check in a branch ruleset.

For production, pin third-party actions to reviewed commit SHAs. Keep intentional exceptions in tool configuration.
