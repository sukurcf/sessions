One review habit. Two places to use it.

Review a selection or working changes in VS Code. Ask Copilot to review a pull request on GitHub.com.

VS CodeLocal review
  • Select code, then choose Generate Code → Review.
  • Or run Copilot Code Review - Uncommitted Changes from Source Control.
  • Read comments inline and in the Comments or Problems view.
  • Accept or discard a suggestion. Applied edits are not committed automatically.
GitHub.comPull request review
  • Open the pull request and add Copilot under Reviewers.
  • Copilot posts a review summary and comments on changed lines.
  • Use the findings to decide what to fix, ignore, or discuss.
  • Hand suitable comments to Copilot cloud agent with Fix with Copilot.
Same rule

Summary + comments

Copilot leaves a review summary and inline comments for issues it finds. Comments show a High, Medium, or Low severity.

Where it can, Copilot includes a suggested code change. It does not comment on every line.

Default

Copilot normally submits a Comment review, not an approval or a request for changes. Treat each comment as a signal to check.

What a Copilot review does — and does not do

The review summary gives context. Inline comments point to specific changes.

It canReview output
  • Report likely bugs, security risks, and style problems.
  • Use repository context, instructions, and configured MCP tools when relevant.
  • Offer code suggestions you can apply with a few clicks.
  • Include an approval assessment in the overview comment.
It does notHuman responsibility
  • Prove that the code is correct or secure.
  • Replace tests, required checks, or a human review.
  • Count as an approval by default.
  • Always re-review a new push unless a re-review rule is enabled or requested.
Read the diff

Confirm the issue in context. Run the checks. Then choose whether to apply the suggestion, ask for a fix, or resolve the comment.

Repository administrators can set defaults. Rulesets decide when Copilot reviews automatically.

Automatic reviews

Review new pushes
Request another review for every new commit after the first review.

Authorized users

Give Copilot instructions it can use

Put durable review expectations in repository files. Keep instructions specific, testable, and easy to maintain.

# Review guidance

- Check error handling at external service boundaries.
- Confirm that authorization checks cover each new route.
- Do not flag generated files or established patterns.
- Run the relevant tests before suggesting a fix.
.github/copilot-instructions.md # repo-wide
.github/instructions/api.instructions.md # matched paths
AGENTS.md # shared agent rules
.github/skills/code-review/ # review workflow

The user's Use custom instructions preference is on by default. Copilot reads review instructions from the pull request's head branch.

Use path-specific instructions for local rules. Use a review-focused skill for a repeatable review workflow.

MCP adds repository review context

Connect Copilot code review to read-only data from tools such as issue trackers, SonarQube, or Wiz.

PR + instructionsDiff, issue key, and review criteria
→
Repository MCPTools enabled in Settings → Copilot → MCP servers

Grounded reviewUse relevant external findings as context

What to configure

  • Repository admins add JSON under Settings → Copilot → MCP servers.
  • Repository MCP configuration is shared by code review and cloud agent.
  • Add credentials as Agents secrets or variables named COPILOT_MCP_*.

What to protect

  • Allowlist only the tools the review needs.
  • Code review filters out tools without readOnlyHint: true.
  • Tools run without a per-call approval prompt. Do not expose write tools.

GitHub and Playwright MCP servers are enabled by default. The Allow Copilot to use MCP tools when reviewing pull requests setting is also on by default.

MCP for code review supports tools, not server prompts or resources. Remote MCP with OAuth is not supported by cloud agent or code review.

Use SonarQube findings in a review

Run Sonar analysis first. Then let Copilot query relevant quality and security findings through MCP.

Setup pathSonarQube
  • Set up SonarQube Server or Cloud analysis in CI.
  • Expose the SonarQube MCP server at a reachable HTTP endpoint and add it in repository MCP settings.
  • Set the endpoint's required project or organization details and a scoped token.
  • Allowlist the server's read-only tools for issues or analysis results.

Keep credentials out of JSON. Store tokens as COPILOT_MCP_* Agents secrets. Use a read-only tool allowlist and a least-privilege Sonar token.

{
  "mcpServers": {
    "sonarqube": {
      "type": "http",
      "url": "$COPILOT_MCP_SONARQUBE_MCP_URL",
      "headers": {
        "Authorization": "Bearer $COPILOT_MCP_SONARQUBE_TOKEN"
      },
      "tools": ["<approved-read-only-tool>"]
    }
  }
}

HTTP template: use the MCP endpoint and auth format from your deployment. Do not use the SonarQube application URL unless it serves MCP. Replace the tool name with an exposed read-only tool.

Use Wiz context without giving write access

Use the same repository MCP settings for Wiz. Choose the transport and authentication that your Wiz deployment supports.

Useful review contextWiz
  • Cloud resources, exposures, or vulnerabilities linked to a change.
  • Repository or pull request text should identify the relevant account, project, or finding.
  • Tell Copilot in custom instructions when to query the Wiz tools and what evidence to report.
  • Use read-only tools. Confirm the exact tool names and transport with your Wiz administrator.
{
  "mcpServers": {
    "wiz": {
      "type": "<server transport>",
      "url": "<Wiz MCP endpoint>",
      "headers": {
        "Authorization":
          "Bearer $COPILOT_MCP_WIZ_TOKEN"
      },
      "tools": [
        "<approved-read-only-tool>"
      ]
    }
  }
}

This is a shape, not a paste-ready config. Replace transport, endpoint, authentication, and tool names with the supported values for your Wiz deployment. Do not use OAuth remote MCP; it is not supported here.

Batch related fixes, then hand them back

Use one clear work request for a related set of findings. Keep unrelated changes separate.

Collect

Group related Copilot findings. Record the file, line, reason, and expected result for each one.

Delegate

Choose Fix with Copilot on a Copilot review comment. Add the other related findings to the draft hand-off.

Choose output

Ask for a commit to the same PR or a new PR against your branch. Review the diff and checks before merge.

For suggestions

Apply one suggestion or a compatible group of suggestions in a single commit. For wider changes, use the cloud-agent hand-off instead.

Re-review after the fix. A push does not trigger another review unless automatic review of new pushes is enabled or you request it.

Agree on the pilot scope

Start with a small, shared question. Do not judge a tool before the team agrees on what a useful result means.

ObjectiveWhat will we learn?

Test whether Copilot review gives developers useful feedback on draft and open pull requests, and whether the hand-off can help with fixes.

Team and repositoryWhat is in scope?

Name the pilot repository, participating developers, review types, and any paths or pull requests that are out of scope.

Success measuresHow will we judge it?

Agree targets for verified findings, false positives, useful fixes, time to review, and developer feedback before you start.

Operating principleWho decides?

Copilot suggests. Developers verify. CI checks. The people responsible for the repository decide what can merge.

Set the review rules before the PR

Use this checklist to explain why a review runs, which context it uses, and what authority it has.

Review trigger
Manual request in the UI or API, personal automatic review, or an organization/repository ruleset. These sources work independently.
Draft pull requests
Enable Review draft pull requests in the applicable automatic-review setting or ruleset to get feedback before publication.
New pushes
Enable Review new pushes to request a new review after each push. Otherwise, request a re-review manually.
Review effort
Balanced is the current default. Select Lite for targeted, routine feedback or Balanced for complex or sensitive changes.
Repository instructions
Check .github/copilot-instructions.md, path-specific instructions, and AGENTS.md. Review instructions come from the PR head branch.
Approvals
A normal review is a comment. Count Copilot approvals toward merge requirements only when policy explicitly allows it.
Output

Configuration checklist: confirm the trigger, draft/push behavior, review effort, instruction files, and approval policy.

Check the runner and the review scope

The runner powers extra review context. Some files are excluded, so make sure your demo uses code Copilot can review.

RunnerGitHub Actions
  • Copilot uses a standard GitHub-hosted runner by default for agentic context gathering.
  • Larger GitHub-hosted runners can improve performance and use more Actions minutes.
  • Use self-hosted runners only through ARC-managed scale sets on Ubuntu x64 Linux.
  • If GitHub-hosted runners are disabled, the review can fall back to a more limited experience.

Use .github/workflows/copilot-code-review.yml for a separate review environment. Without it, Copilot can use copilot-setup-steps.yml.

Review scopeFiles and context
  • Default exclusions include dependency files, lock files, logs, and SVG files.
  • Generated, vendored, built, and bundled files are also commonly excluded.
  • Organization content-exclusion rules can hide additional paths from Copilot.
  • Instructions and skills used for a review must be on the pull request's head branch.

Do not use a lock file or generated file as the only example in a live review.

Safety note

GitHub documents ARC as the only supported self-hosting option for Copilot code review. Do not use a general-purpose self-hosted runner.

Choose Lite or Balanced

Use one routine pull request and one complex pull request to explain the choice of review effort.

LiteRoutine PR

Use for a smaller, lower-risk change when fast, targeted feedback is enough.

  • Look for common bugs, security issues, and style problems.
  • Record what was useful and what it missed.
BalancedComplex PR

Use for complex logic, security-sensitive code, or changes across services.

  • Expect deeper analysis and higher AI-credit use than Lite.
  • Record the effort shown in the review overview.
Compare

Show the effort in each overview comment and the review sequence in the PR timeline. Record time, AI credits, Actions minutes, and verified findings when available. Different PRs are a demonstration, not a controlled benchmark.

Balanced is the default since September 28, 2026. Effort can be set per request. Large pull requests no longer have the former 300-file or 20,000-line limit, but Copilot may still miss findings. Automatic reviews of bot-authored PRs require the organization policy for members without a Copilot license and paid AI credits; usage is billed to the organization.

Output

Effort-level comparison: example reviews, effort labels, and notes about findings, time, and usage.

Review each comment in context

Severity and grouped suggestions help with triage. They do not confirm that a finding is correct.

Read the reviewOverview + inline
  • Use High, Medium, and Low labels to prioritise comments.
  • Copilot groups similar suggestions to reduce repeated comments.
  • The overview groups findings as open, resolved since last review, or previously missed.
  • Follow a comment link to check the actual code and evidence.
Make a decisionHuman check
  • Verify the issue in context and run the relevant tests.
  • Accept or reject a suggested change. Batch compatible suggestions when it helps.
  • Resolve with a reason: Addressed, Won't fix, or Incorrect.
  • Replies are visible to people on the PR; Copilot does not read or answer them.
Output

Comment-quality sample: one verified finding, one useful suggestion, and one decision with a clear resolution reason.

Repository and paths

Make style checks repeatable in GitHub

Run Markdownlint and Codespell as pull request checks. Let CI report deterministic issues; let Copilot explain code context.

name: Content checks
on:
  pull_request:
permissions:
  contents: read
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: DavidAnson/markdownlint-cli2-action@v24
        with:
          globs: '**/*.md'
      - uses: codespell-project/actions-codespell@v2
Wire it into merge policyGitHub Actions
  • Put workflow files in .github/workflows/.
  • Configure Markdownlint rules in .markdownlint-cli2.jsonc.
  • Configure Codespell in .codespellrc or pyproject.toml.
  • Require the job as a status check in a branch ruleset.

Use the same commands locally. Agree on intentional exceptions in the tool's config, not by hiding failed checks.

Pin Actions to reviewed versions or commit SHAs for production workflows. Check each action's current usage and permission guidance.
